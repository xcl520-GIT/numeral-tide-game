# 设计迭代记录 · 数值潮汐

这份文档记录的是一个**被数据反复推翻的设计过程**。

原始需求只有一句话：

> 开局自己为 1，敌人也是 1，我可以击败 1 然后升级成 2；
> 如果敌人这时候大于 2，我与他战斗后就会死亡。

从这句话到最终能玩的版本，中间有 **三次整机制被推翻**。
每次推翻都不是"感觉不好玩"，而是模拟器跑出了明确的数字。

---

## 前提：这个需求的最优解是唯一的

先看原始规则：

- 玩家数值 P，敌人数值 E
- `P >= E` → 击败，`P += 1`
- `P < E` → 死亡

假设场上敌人数值是 `[1, 1, 3]`，你 P = 1。

唯一能打的是 1。打完 `P = 2`，场上变成 `[2, 3]`。再打 2 → `P = 3`。
**整个过程没有任何选择**，"能打的里面挑一个"就是全部策略。

**结论：这套规则能跑起来，但它的决策空间为零。** 必须先补一层机制。

补什么？我的判断是：**让"成长"和"时间"变成同一件事的两面**。

---

## v1 · 敌人每回合成长

**假设**：玩家每回合最多吃一个敌人；如果敌人也在同步变强，
"先吃谁"就变成了"在什么时间窗口内吃"的问题 —— 决策自然出现。

**规则**：
- 玩家吃敌人得 `P += E`（吃掉对方的数值）
- 每回合结束，**所有敌人 +1**

**模拟结果（1000 局）**：

```
通关率 31.2%   平均回合 197.0   平均吞噬 8.38/20
```

**结论：失败。而且失败的方式比数字更糟 —— 它暴露了一个结构性缺陷。**

原因是一个**活锁**：

```
玩家吃不到东西  →  数值停滞
      ↑                ↓
敌人继续按 +1 增长  ←  可吃的目标越来越少
```

玩家一旦进入"场上所有敌人都比我大"的状态，就**永远出不来**了 ——
他只能一直躲，躲到回合上限。这解释了那 197 的平均回合。

> **教训**：只要"敌人成长"和"玩家必须移动才能吃"这两条同时存在，
> 就一定存在这个活锁。**这不是调参能解决的，是机制本身不自洽。**

---

## v2 · 敌人不再变强，压力改为"涌入"

**修正思路**：把时间压力从"敌人变强"换成"空间被填满"。

**规则**：
- 敌人数值**恒定不变**（老敌人永远可以回头吃 → 活锁从结构上消失）
- 每 N 回合从随机空位刷新一个新敌人，数值随玩家缩放
- 敌人数量达到阈值 → 判负（"被淹没"）

**模拟结果（1500 局）**：

```
通关率 99.9%   平均回合 89.4   死因[撞死 0  淹没 1  困死 0  超时 0]
```

**结论：活锁确实消失了（超时 0、困死 0），但游戏也死了。**

关键在那一行 **"撞死 0"**：

> 因为敌人数值恒定、且完全可见，玩家可以做到**完美规划** ——
> 永远不碰任何吃不下的目标。风险决策 = 0。

于是游戏退化成"扫地"：把能吃的挨个吃掉，等刷新，继续吃。
**玩家不会输，也就不存在张力。**

> **教训**：确定性 + 完全信息 + 静态敌人 = 最优策略可被穷举。
> 想让玩家"必须冒险"，就得让他**不得不做取舍**。

---

## v3 · 引入"礁石"，把压力换成空间

**假设**：加一种**永远吃不掉、只占格子**的障碍（礁石），
让它持续堆积、压缩活动空间 —— 玩家会在"必须清路"和"必须抢分"之间被迫取舍。

**规则**：
- 新增礁石，数值 = 玩家数值 × `[2.0, 3.5]`（吃不到）
- 每 N 回合沉积一块

**模拟结果（600 局，扫描后）**：

```
wall_every=1   通关  68.0%   回合  98.0   死因[撞死 0  淹没 81  困死 111]
wall_every=2   通关  96.5%   回合  93.0
wall_every=3   通关  99.2%   回合  87.2
```

**第一次出现了像样的难度曲线** —— 通关率从 100% 掉到 68%，
死因也从"没有死因"分裂成"淹没 / 困死"两类。

**但还有一个问题**：礁石按**玩家数值的比例**生成，意味着它**永远比玩家强 2~3.5 倍**。
玩家永远吃不掉它们 → 空间只减不增 → 是单向挤压，不是博弈。

体验上会变成"眼睁睁看着自己被困死"，而不是"我在和潮水赛跑"。

---

## v4 · 礁石改用绝对数值（定稿）

**修正**：礁石数值不用玩家比例，改成**绝对数值 + 随回合线性增长**：

```
礁石数值 = 6 + 当前回合数
```

这么一改，曲线形状完全不同了：

- **前期**：你只有 1，礁石是 6 —— 它就是一堵墙
- **中期**：你靠吞噬指数成长，很快追上礁石
- **后期**：你反手就能砸开它，把被吃掉的空间抢回来

于是形成 **「被压迫 → 突破 → 反打」** 的成长曲线，
而不是 v3 那种单向挤压。

**参数网格搜索（18 组合 × 600 局）**，选死因最分散的一组：

```
spawn=3  wall_base=6  wall_scale=1.0
通关  85.8%   回合  96.7   吞噬 22.86   死因[撞死 0  淹没 38  困死 47]
```

**定稿验证（2000 局）**：

```
通关  85.2%   回合  96.1   吞噬 22.61   死因[撞死 0  淹没 113  困死 182]
```

## 最终参数

```python
W = 9, H = 9              # 81 格棋盘
player_start = 1
initial_enemies = 6
initial_enemy_max = 2

spawn_every = 3           # 每 3 回合涌入一个普通敌人
spawn_lo = 0.30           # 普通敌人数值 = 玩家数值 x [0.30, 1.10]
spawn_hi = 1.10

wall_every = 1            # 每回合沉积一块礁石
wall_base = 6             # 礁石数值 = 6 + 回合数 x 1.0
wall_scale = 1.0

goal = 25                 # 吃满 25 个普通敌人通关
```

## 四版对比

| 版本 | 核心机制 | 通关率 | 平均回合 | 致命缺陷 |
|---|---|---|---|---|
| v1 | 敌人每回合 +1 | 31.2% | 197.0 | **活锁** —— 吃不到就永远吃不到 |
| v2 | 静态敌人 + 涌入 | 99.9% | 89.4 | **零风险** —— 最优解可被穷举，撞死 0 次 |
| v3 | 礁石（按玩家比例） | 68.0% | 98.0 | **单向挤压** —— 礁石永远吃不到 |
| **v4** | 礁石（绝对数值） | **85.2%** | **96.1** | 定稿 |

## 三条可以迁移到别处的经验

**1. 数值系统的 bug 往往不是"不平衡"，而是"不可能"**

v1 的问题表面看是"太难"（通关率 31%），实际是那个活锁 ——
玩家**在数学上已经无解**了，只是程序还在让他继续走。
如果不看"平均回合 197"这个异常值，很容易误判成"再调调参数就好"。

> 排查心法：**当平均回合数接近你设的上限时，八成是活锁，不是难度。**

**2. 同一个旋钮，改标量还是改比例，会得到完全不同的游戏**

v3 和 v4 只差礁石的数值怎么算（玩家比例 vs 绝对数值），
但一个是"绝望的挤压"，一个是"有来有回的反打"。

**3. 难度参数是可以被搜索出来的**

`tools/sim.py` 的 `sweep` 和 `tune` 两个模式一共跑了十几万局，
整个过程没有一次是靠"感觉"调的。
这也是为什么这个项目能给出下面这种可验证的结论：

> 定稿参数下，Python 与浏览器两套实现，跑同一批 300 个 seed：
> **通关 83.0% / 回合 95.6 / 吞噬 22.28 / 淹没 22 / 困死 29 —— 逐位一致。**

---

## 还没解决的

- 贪心 AI 的"撞死"恒为 0，说明**风险决策对人类足够明显，但对 AI 不够**。
  真正的决策深度可能要靠"信息不完全"（比如敌人数值只显示区间）才能真正做出来
- 没有构筑系统。每局的差异只来自随机地图，缺少 roguelike 的"这一把我要玩什么流派"

# 第二阶段：从"能玩的机制"到"能交付的作品"

v4 结束时的状态是：机制成立、平衡已验证，但**它还不是一个作品** ——
没有难度分层、没有构筑维度、没有视听反馈、也没法给别人玩。

这一阶段要解决的是另一类问题。

## v5 · 内容扩展，把「机制」变成「玩法」

### 加入的四层东西

| 层 | 内容 | 为什么加它 |
|---|---|---|
| 构筑 | 15 件遗物，每 8 个吞噬三选一 | 让"这一把要玩什么流派"成为真问题 |
| 难度 | 休闲 / 标准 / 深渊 / 每日挑战 | 让玩家的技术成长有刻度 |
| 生态 | 游走者 · 膨胀体 · 分裂核 · 孢子巢 · 遗物匣 | 让棋盘不再是一堆同质的数字 |
| 反馈 | 合成音效 · 粒子 · 震屏 · 数字弹出 | 让每一次吞噬"有手感" |

### 遗物的设计原则：改规则，不是加数值

第一版我写的遗物是"吞噬收益 +10%"这种纯数值加成 ——
模拟跑下来发现它对**决策**毫无影响，只是把胜利提前了几回合。

推倒重来后定了一条原则：**每件遗物都必须改变某个约束的边界**。

- 「破礁锤」把"砸礁石不计分"变成计分 → 整局策略从"绕着走"变成"主动清路"
- 「猎手直觉」把可吞噬阈值抬到 1.3 倍 → 能吃的东西突然多了一圈
- 「缓潮之锚」把礁石沉积从每回合改成每两回合 → 时间预算直接翻倍
- 「时间沙漏」直接抹掉全场礁石 → 相当于一次"重新开局"的机会

**判据很简单**：拿到它之后，你的下一步会不一样吗？
如果答案只是"数值更大了"，那就重做。

### 难度标定：先扫曲面，再选点

新增了 `?scan=1` 入口，扫描 `wallBase × wallScale` 的二维参数曲面
（2 个难度 × 4 个 base × 3 个 scale × 120 局）。摘录一段：

```
standard  base= 6 scale=1.0  →  90.8%   回合 81.9
standard  base= 9 scale=1.4  →  83.3%   回合 83.1
standard  base=12 scale=1.4  →  79.2%   回合 80.0
standard  base=15 scale=1.4  →  68.3%   回合 78.2
abyss     base= 9 scale=1.8  →  60.8%   回合 69.8
abyss     base=12 scale=1.8  →  58.3%   回合 68.6
abyss     base=15 scale=1.8  →  56.7%   回合 69.0
```

**三档难度就是照着这张表落点的**，中间没有一次"感觉好像有点难"。

第一轮定标后实测（400 局）：

| 难度 | 第一版结果 | 问题 | 第二轮调整 | 最终 |
|---|---|---|---|---|
| 休闲 | 97.0% | 几乎不会输 | wallBase 7→10, scale 0.8→0.95 | **95.8%** |
| 标准 | 90.8% | 太宽松 | wallBase 6→14, scale 1.0→1.5 | **72.7%** |
| 深渊 | 75.0% | 与标准几乎无差 | wallBase 16→20, scale 2.0→2.5, goal 30→32 | **53.5%** |

两轮之后梯度才拉开：**96% → 73% → 54%**。

> **教训**：`base` 这个旋钮有**递减效应** —— 从 6 提到 9 掉 4 个点，
> 从 12 提到 15 只掉 7 个点里的一半。想跨越大区间，必须同时动 `base`、
> `scale` 和 `goal` 三个杠杆，只推一个会撞墙。

### 顺带修掉的一个真 bug

模拟输出的死因分布里出现了 **4 个空字符串**。查下去发现：

> 玩家四面都被吃不下的敌人包围、**但身上还有护盾**时，
> 核心逻辑认为"还能撞开"，不判定被困；而 AI 策略认为"没有安全的走法"，返回 null。
> 两边对"能不能走"的判断不一致，于是游戏卡在半空中。

修了两处：AI 学会"有护盾就撞最弱的目标"，同时给任何异常退出兜底一个 `stuck` 死因。

> **教训**：**当统计里出现你没定义过的取值，那多半不是数据问题，是状态机漏了一条路径。**

## v6 · 桌面化：怎么把网页变成"一个 exe"

用户的要求很具体：**双击一个 exe 就能玩，整个游戏在最外层只有一个文件夹，
可以直接传网盘给别人。**

### 技术路线是探明出来的，不是选出来的

先探测环境，结果决定了方案：

| 探测项 | 结果 | 影响 |
|---|---|---|
| Node.js | 缺失 | Electron / NW.js 出局 |
| Chrome | 缺失 | 只能指望 Edge |
| pyinstaller / pywebview | 未安装 | Python 打包出局（且不该擅自装） |
| **`csc.exe`（.NET 编译器）** | **系统自带** | ✅ 可以直接手写 C# 编译 exe |
| **WebView2 Runtime** | **已安装 (153.x)** | ✅ 可以做**真正的原生窗口** |

所以最终方案是：

```
C# 启动器（自己开 WinForms 窗口）
    └─ 内嵌 WebView2 控件（系统自带运行时）
          └─ 把 www\ 目录映射成虚拟域名，加载 index.html
```

**不是"启动浏览器打开网页"，而是一个有自己的进程名、标题栏和图标的应用窗口。**

### 为什么要映射虚拟域名

WebView2 提供了 `SetVirtualHostNameToFolderMapping`，把本地文件夹
挂到一个假域名（`numeral-tide.local`）下。这样做而不是直接用 `file://`，
是因为 `file://` 下的页面 origin 是特殊的，`localStorage` 这类能力会被限制 ——
而游戏需要它来存"最佳成绩"。

### 发行版结构

```
数值潮汐\
├─ 数值潮汐.exe                    76.5 KB  ← 双击这个
├─ Microsoft.Web.WebView2.Core.dll  923.8 KB
├─ Microsoft.Web.WebView2.WinForms.dll 37.8 KB
├─ WebView2Loader.dll               190.3 KB
├─ www\                             游戏本体（9 个文件，约 70 KB）
└─ 说明.txt
```

总计约 **1.2 MB**，拷走即玩，不需要管理员权限、不需要安装。

### 这一段踩的坑（值得单独记）

**坑 1：PowerShell 的编码**
`build.ps1` 里写了中文注释，脚本直接报语法错误。原因是
Windows PowerShell 5.1 会按 **GBK** 解析无 BOM 的 `.ps1`，
中文被拆成乱码后连引号都配不上对了。
→ 修复：`build.ps1` 与 `launcher.cs` 都必须存成 **UTF-8 with BOM**。

**坑 2：`Say "x" + $y` 不是字符串拼接**
`Say` 是个只收一个参数的函数，`Say "a" + $b` 里 `"a"` 成了第一个位置参数，
后面的 `+ $b` 变成了另一段表达式，报出 `op_Division` 这种莫名其妙的错。
→ 修复：整个表达式加括号 `Say ("a" + $b)`，或者先算好再传。

**坑 3：并行编辑同一个文件会丢改动**
同一轮里对 `main.js` 发了 5 个替换，结果其中 1 个报"未找到"、文件末尾还被追加了残留内容。
→ 修复：**同一文件的编辑必须串行**，或者干脆一次性整段替换。

**坑 4：.NET 编译器的路径参数**
`"/r:" + (Join-Path $lib "x.dll")` 这种写法在数组里会被 PowerShell 拆错，
csc 报 `"/r:" 选项缺少文件规范`。
→ 修复：先算进变量再插值 `"/r:$coreDll"`。

### 图标：手写 PNG

不想为了一个图标引入 Pillow，所以用标准库 `zlib` + `struct` 手写了
PNG 编码器（IHDR / IDAT / IEND 三个 chunk + CRC32），再套上 ICO 容器头，
一次性输出 16 / 32 / 48 / 64 / 256 五个尺寸。

图形语言和游戏一致：深海径向渐变底 + 一颗发光的主球 + 底部三道上涨的潮线。

> 整个发行版**没有一个图片或音频文件** ——
> 图标是算出来的，音效是合成的，粒子是运行时生成的。
> 这也是它为什么只有 1.2 MB。

# 第三阶段：换掉骨架

v6 交付之后，用户给了三条反馈，其中一条是致命的：

> **「大鱼吃小鱼跟我们的好像没啥差别。」**

他说得对。v1~v6 做的所有事情 —— 礁石、遗物、难度、桌面化 ——
都建立在"比大小"这个骨架之上。而**比大小的一次遭遇，全部信息就是两个数字**，
所以"打不打、打谁"必然退化成排序问题。

加遗物只是给这个骨架贴装饰。要变好玩，得换骨架。

---

## v7 · 从「比一个数字」到「比两个面板」

### 新的战斗模型

```
伤害 = 攻击 × 50 / (有效防御 + 50)
有效防御 = max(0, 防御 − 对方穿透)
```

这个公式本身不稀奇（就是标准的递减减伤）。它值钱的地方在于**制造了偏科的空间**：

- 石甲兽 物防 24 / 法防 **0** → 法术伤害几乎翻倍
- 幽魂 物防 **0** / 法防 26 → 必须用物理
- 疾风兽 双防都低但速度 24 → 每轮多打你一次

而且**攻击方式由系统自动择优**（比较两路实际伤害，取高的）。
这样"针对性"会自然体现在伤害数字上，不需要玩家手动切技能。

### 真正让决策成立的，是这一条

> **每场战斗都会掉血，回血极少。**

于是每个决定都变成成本核算：打得赢 ≠ 打得值。

为了让这条成立，战斗必须**短**——因为回合数直接等于挨打次数。

第一次配平衡时，玩家初始 12 物攻、黏液怪 42 血，打一场要 4 轮、掉 25 血（占总量 23%）。
而目标是 18 杀 —— 数学上不可能。模拟结果印证了这一点：

```
初版：通关 0%  平均击杀 5.31  平均死亡回合 55
```

把玩家初始攻击从 12 提到 **36**（把战斗压到 2 轮），并下调敌人血量后，
才回到可玩的区间。

## 这一段踩的三个坑（都很隐蔽）

### 坑 1：`undefined` 让整条算式变成 NaN

模拟第一版跑出来是这样的：

```
通关 0.0%   回合 1199.3   击杀 3.19   {"slain":0,"stuck":300}
```

**回合数贴着上限、击杀数极低、而且一局都没死过。** 这三个信号放在一起，
指向的不是"太难"，而是 **AI 根本没出手**。

根因在伤害函数里：

```js
const eff = Math.max(0, def - pen);
```

敌人的模板里**没写 `penP` 字段**，于是 `def - undefined` = `NaN`，
整条算式被污染成 `NaN`。而 `Math.max(1, NaN)` 依然是 `NaN`，
所以 AI 的胜负判断 `pRounds <= eRounds` 变成 `4 <= NaN` —— **恒为 false**。

> **教训**：`NaN` 不会报错，它只会安静地把所有比较变成 false。
> 凡是跨模块传数值的地方，缺字段必须补 0，不能指望对方一定有。

修复后同样的代码：

```
回合 1199.3 → 57.6    slain 0 → 288    stuck 300 → 12
```

### 坑 2：`Object.assign` 会静默覆盖同名字段

修好 NaN 之后，我做了参数扫描，结果和实测差了 **5 倍**：

| 路径 | 通关率 |
|---|---|
| 调参台（带 overrides） | 53.5% |
| 实际模拟（读难度配置） | 10.0% |

两条路径跑的是同一套逻辑、同一个配置值。差异只可能来自配置本身。

根因在 `core.js` 拼配置的这一行：

```js
this.cfg = Object.assign({}, D.BOARD, D.DIFFICULTIES[key], D.COMBAT);
```

**`D.COMBAT` 里也有一份 `healAfterWin: 0.05`**，而它排在最后 ——
于是难度表里精心设定的 `0.13` 被**静默覆盖**成了 `0.05`。
调参台因为 overrides 应用在最后，反而绕过了这个坑。

> **教训**：`Object.assign` 的后者覆盖前者是**静默的**。
> 当多个配置源合并时，**同名字段必须只存在于一个源里**。

修复方式不是调顺序（那只是把问题挪走），而是**把重复字段从 COMBAT 里删掉**，
并在那里留了一行注释说明为什么不能加回来。

### 坑 3：先怀疑缓存，结果不是

上面那个 5 倍的差异，我第一反应是浏览器缓存了旧的 `data.js`。
加了 `?v=3` 版本号、强制刷新之后 —— **还是 10%**。

这才回头去查配置合并。

> **教训**：缓存问题确实很常见（这个项目里也真的遇到过），
> 但**不要在验证之前就把它当成结论**。加版本号只花了两分钟，
> 排查配置合并花的时间更长 —— 顺序错了。

## 平衡：三维参数曲面

新的参数比旧版多，所以把调参台做成了三维扫描：

```
atk=22  scale=0.06  heal=0.10  →    7.3%
atk=30  scale=0.06  heal=0.16  →   59.3%
atk=38  scale=0.06  heal=0.16  →   80.7%
atk=38  scale=0.10  heal=0.10  →   22.0%
atk=38  scale=0.10  heal=0.16  →   56.0%
atk=38  scale=0.14  heal=0.16  →   23.3%
```

规律很清晰：**`heal` 和 `atk` 是主导旋钮，`scale` 影响次之**。
（`heal` 从 0.10 到 0.16 能让通关率翻倍；`scale` 从 0.06 到 0.14 能砍掉一半。）

照表落点 + 两轮实测微调，最终：

| 难度 | 通关率 | 平均回合 |
|---|---|---|
| 休闲 | 85.3% | 23.3 |
| 标准 | 64.5% | 30.3 |
| 深渊 | 30.5% | 31.8 |

## v8 · 补上"收束"

换掉骨架之后出现了一个新的设计漏洞：**玩家可以无限躲避**。

旧版有礁石沉积制造空间压力，新版把礁石删掉之后，躲避变成了零成本行为。
表现就是模拟里的 `stuck` —— AI 一直绕圈，游戏永远不结束。

补法是让**敌人每 5 回合朝玩家推进一格**：

```
stuck 9 → 0        回合 65.4 → 29.2
```

有意思的是，这个改动同时解决了两个问题：既堵住了无限躲避，
也让游戏节奏更紧凑（29 回合完成 14 次击杀）。

# v9：潮汐地牢（地图 / 职业 / 装备 / 全面重做视觉）

## 起因：四条反馈

1. 视觉效果很一般，主黑色，看起来很基础；要加地图机制
2. 要一个**有吸引力的开始界面**
3. 加机制概念：职业选择（效果不同 / 外观不同 / 武器不同）、
   地图机制（移动范围太小，单格移动要保留为"基底"，但长按能持续走更远）、
   装备机制（多槽位、敌人掉落、多品质、词条、爆率）
4. 角色要有背包、**明显的属性栏（英雄联盟那种）**、地图外观要丰富

第 3 条里的"单格移动保留为基底"是这轮最重要的一句约束 ——
它不是"加一个功能"，而是要求**在移动这件事上做层次**。

---

## 1. 地图：从 7×7 DOM 棋盘到 45×35 洞窟

旧版是一个 7×7 的 `div` 网格，一眼看完，没有"探索"这回事。

新版：

- **BSP 房间 + 走廊**，45×35，再补 4 条捷径形成环路
- **相机跟随 + 视野**（半径 8.5，射线法遮挡）三态：未探索 / 记忆 / 可见
- 地形 9 种：地板、墙、水、苔草、岩浆、门、宝箱、泉水、潮汐之门
- 装饰层 5 种：碎石、骸骨、木桶、木箱、火盆（沿房间边缘摆放，中间留空）
- 右上角小地图

墙用**顶面受光 + 正面背光 + 交界高光线**画，再给相邻地板叠一圈 AO 阴影。
这一条比任何调色都管用 —— 墙一旦"立起来"，画面立刻不像色块了。

### 移动（按用户要求做成三层）

| 层次 | 行为 |
|---|---|
| 基底 | 方向键 / WASD / 点击相邻格 → **走一格** |
| 长按 | 按住不放 → 连续走，松手即停（首次延迟 175ms，之后每 92ms） |
| 目标 | 点击远处 → A* 寻路自动走，画面上有青色路径点；长按鼠标则持续跟踪目标 |

三种方式**最终都拆成同一次 `stepTo()`**，所以规则只有一份，
不会出现"点着走能穿墙、按键盘不能"这类不一致。

---

## 2. 潮汐：把游戏名字变成机制

旧版的"潮汐"只是一个比喻。这一版让它变成字面意义上的水位。

- 水位按 `0 → 1 → 2 → 3 → 3 → 2 → 1 → 0` 循环（完整周期 7 个节拍）
- 水面 = 「从水洼出发、步数 ≤ 当前水位」的所有地板格，用 BFS 重算
- 涨潮时通路变窄、踩水掉血；退潮时退回原位，是绕路/开箱/找泉水的窗口

### ✗ 第一版做错了

一开始的规则是"水位只涨不跌，到顶后不断从水源长出新水域"。

模拟结果：**60 局里 27 局死于潮水，15 局因为全图被淹而 AI 卡死。**

问题不在数值，在于**没有节奏**：

> 单向的水位不是"压力"，而是一台死亡时钟。
> 玩家既没有喘息窗口，也没有"趁退潮去探险"的决策 ——
> 所有决策都被压缩成"能不能在死之前跑完"。

改成周期性涨落后，潮水致死直接归零。

**教训：压力机制必须给玩家一个"可以有所作为"的窗口。
只增不减的计时器不叫难度，叫处刑。**

### 为什么需要一份「基准地形快照」

水面不是"逐格往上涨"，而是**每次都从 `this.base` 重算**。

没有 `base`，退潮时不知道该把水还原成什么，水面会一路只增不减 ——
这是必须留的一份快照，不是可选优化。

## 3. 职业：让武器和职业在结构上绑定

四个职业：破军（巨剑）/ 秘仪（法杖）/ 疾风（长弓）/ 铁壁（锤盾）。

外观用**参数化纸娃娃**绘制：一段身体（按职业配色）+ 一把按 `cls.weapon` 分支画的武器。
这样"法师拿木桶"这种事在数据结构上就不可能发生。

被动都遵循同一条原则：**改变一个约束边界，而不是加数值**。

- 破军：每击杀永久 +2 物攻 +1 物穿（成长曲线形状变了）
- 秘仪：法术击杀回 10% 生命（补掉法师最缺的续航）
- 疾风：第一轮必定先手且 +40%（把"速度"变成"首轮爆发"）
- 铁壁：残血双防 +60%，战后回 8%（把"低血"从危险变成资源）

## 4. 装备：22 基底 × 5 品质 × 21 词条

- 5 槽位：武器 / 头盔 / 胸甲 / 靴子 / 饰品
- 5 品质，词条数 0/1/2/3/4，数值系数 1.00→2.15
- 12 条数值词条 + 9 条**机制**词条（荆棘、回响、处决、血契、连击、吞噬…）
- 掉率：普通 34% / 精英 +32% / 宝箱怪必掉 / 首领必掉且取两件里更好的

### 属性栏按"常驻侧栏"做，而不是按 I 才弹出

这是个纯属性对抗的游戏。玩家每一个决策（打谁、走哪、换哪件装备）
都依赖当前面板。把面板藏起来，等于让玩家闭着眼睛做决策。

所以：主属性常驻，装备槽常驻，只有背包可折叠。

### 鼠标移到敌人身上要直接给结论

"这一刀该用物理还是法术"依赖 `攻击 × 50 / (防御 − 穿透 + 50)` 的实时比较。
让玩家心算是不合理的，所以悬停直接把结论算好：

> **建议法术：每轮约 34，3 轮击杀 / 预计这场要掉 58 血（当前 210）**

### 装备气泡必须有「和身上那件比」

掉落装备的意义全在于此。逐项差值直接用红绿标出来，不让玩家自己记账。

## 5. 验证方式的升级：从"两份实现"到"同一份 JS"

旧流程是 `tools/sim.py` —— 用 Python **复刻**一遍核心逻辑。
它当时很有用，但有一条根本隐患：

> 两份实现一旦漂移，平衡数据就全是假的。
> 这个坑已经踩过一次（`Object.assign` 静默覆盖字段，导致 sim 与扫描台差 5 倍）。

这一版换掉了：**用系统自带的 Edge 无头模式直接跑 `src/js/core.js`**。

```powershell
& $edge --headless=new --dump-dom "file:///.../tools/sim.html?n=240&diff=all"
```

同一份代码，物理上消除了漂移。附带好处是不再需要维护第二套实现。

### 新增：集成冒烟测试（`tools/smoke.html`）

逻辑模拟器碰不到 DOM 和 canvas。渲染层写错一个函数名、UI 里查一个不存在的 id，
在无头模拟里全都看不出来，但玩家一进去就是白屏。

`smoke.html` 把真实页面塞进 iframe，驱动真实流程并捕获所有未处理异常，
检查 40+ 项，其中三条是这一版真正救命的部分：

1. **真实点击按钮**（而不是直接调 API）
2. **画布像素统计**：平均亮度 / 亮度范围 / 色块种类 / 最亮 15% 的亮度
3. **地图连通性**：出口必须可达、所有敌人必须可达

## 6. 这一轮真正救命的 6 个坑

### 坑 1：`pathToExit: false` —— 岩浆堵死了走廊接口

房间+走廊看起来天然连通，但只要岩浆在走廊接口上留下一个不可通行格，
出口就会整块被隔离。表现：清完怪却永远走不到潮汐之门，**21/60 局卡死**。

修法有两层：岩浆禁止放在房间中心 2 格内（源头），
以及一道**确定性的连通性兜底**（洪水填充 + 必要时强开 L 形应急通道 + 剔除不可达敌人）。

> 地图"生错了"这种 bug 不能靠调数值掩盖，必须有一道自查。

### 坑 2：AI 站在泉水上锁定了自己脚下的格子

血少 → 找泉水 → A* 到自身只返回 1 个节点 → 判定"无路可走" → 每轮原地打转。

**80 局里 36 局卡死。**

两处都改了：泉水改成**一次性**（顺便堵住无限回血蹭血），
以及每个分支必须"尝试后失败就落空到下一条"，不能直接 `return false`。

### 坑 3：阈值抖动 —— 在两格之间无限横跳

每回合从头挑目标 → 站在 A 格时宝箱距离 9（在范围内）→ 走一格到 B；
站在 B 格时距离 10（超出）→ 转回出口，又走回 A。

轨迹记录一眼就能看出来：`15,15 → 14,15 → 15,15 → 14,15 …`

修法是**目标承诺**：选定目标就锁定，直到到达 / 目标失效 / 出现更高优先级的事。

> 这是 AI 编程的经典病。**每帧重新决策 = 在阈值边界上抖到天荒地老。**

### 坑 4：A* 的迭代上限在大地图上不够用

水面代价让搜索节点数膨胀，900 个节点搜不到远端目标 →
"可达"被误判成"走不到" → AI 原地罚站。

修法：上限提到 4000，外加"被堵住就先把贴脸的敌人解决掉"的兜底。

### 坑 5：反复锁定一个走不到的目标

"最近但在孤立区域里"的宝箱，每轮都被重新选中、每轮都失败。
修法：**坏目标黑名单**（本层内不再尝试）。

### 坑 6：吸血型敌人制造永久僵持

祷者 25% 吸血、首领 15~20%。当它每轮回的血 ≈ 你每轮打掉的伤害时，
双方都活着，回合数无限增长。模拟里表现为 8% 的对局跑满 2400 回合；
对真人玩家则是一个死局：**打不死它，也走不掉。**

修法：对决到达 40 轮上限时，**按剩余生命比例判定胜负**。
于是"能不能打赢"重新变成一个可以判断的问题。

## 7. 素材：为什么最后是自己画

用户给了一篇素材站导航文章，并说"看看能不能用"。
文章本身没有素材，它列的是 Kenney / OpenGameArt / Itch.io / Craftpix /
Game-Icons.net / FreeSound / 爱给网 这类站点。

我实际下载评测了 **Kenney Tiny Dungeon**（132 块）和
**Kenney Roguelike RPG Pack**（1767 块）。质量很好，但绕不开：

> 图集是「16×16 密排 + 纯数字编号」，**没有任何语义标注**。

我试过一条不依赖肉眼的自动推断路线，值得记下来：
用 Kenney 自带的 `sampleMap.tmx`（明确记录每格用了哪个 tile 和翻转标志）
+ `Sample.png`，反推图块语义，再用**「重渲染结果与 Sample.png 逐像素求差」**
来**自证映射正确** —— 这是能闭环的思路。

结果 `Sample.png` 是无周期性的营销图（256 色、平滑缩放、与地图网格不匹配），
逐像素比对不成立，路线作废。

猜错的后果是「法师举着一个木桶」这种一眼假的事故，**比画得朴素更伤**。
所以最终走两条都不需要猜编号的路：

| 用途 | 方案 |
|---|---|
| 地形 / 角色 / 怪物 | 代码参数化生成（语义由我定义，物理上不可能错位） |
| 界面图标 | `game-icons.net` 的 SVG，**文件名即语义** |
| 音效 | Web Audio 实时合成（零文件） |

代价是风格偏"现代极简像素"；收益是**发行版里一个二进制素材文件都没有**。

## 8. 修过的一个隐蔽 bug：音频异常会打断按钮

`onclick = function () { TideAudio.ui(); TideMain.start(); }`

音频上下文创建失败（没有声卡 / 被策略拦截）时抛异常 →
`start()` 根本没执行 → **表现为"点开始没反应"，而且完全看不出和声音有关。**

两处都改了：`ctx()` 吞掉创建异常并把音频整个静音；
所有对外音频方法包一层 guard；按钮回调里把 `start()` 放到音效之前。

## 最后再加两条可迁移的经验

**6. 不要用"每帧重新决策"来实现 AI**

三个卡死 bug（泉水自锁、阈值抖动、坏目标重试）本质是同一个病：
**在每一个决策点都从零重算，于是一个微小扰动就能让它永远在两个状态之间振荡。**
解法也是同一个：**承诺 + 失效条件 + 黑名单**。

**7. 你无法目视验收的画面，就用像素统计验收**

看不到画面时，"黑屏"和"正常渲染"在程序上是同一种状态 ——
不抛异常、不报错。所以把验收变成数字：平均亮度、亮度范围、色块种类、
最亮 15% 像素的亮度。这四个指标能兜住绝大多数"画面崩了但代码没报错"的情况。

## 1. "帧率很低"的病根不是帧率

用户看到的是"卡"，但真正的两个原因都不是帧率。

### 病根 A：移动是瞬移

`stepTo()` 直接把整数格坐标写进 `game.px/py`，而渲染层**直接拿它当屏幕坐标用**。
所以每走一步，角色都是从 A 格"跳"到 B 格，中间没有任何过渡。

**逻辑完全正确，但观感上就是卡。** 这和帧率毫无关系 ——
哪怕跑满 144Hz，角色依然是每秒跳十几次。

修法是把逻辑位置和视觉位置分开：

```js
vis.px = approach(vis.px, game.px, 1 - Math.exp(-dt / 46));
```

指数收敛而不是线性插值，好处是**与帧率无关**：60fps 和 144fps 下
同样时间走完同样距离。相机用更大的时间常数（95ms）平滑跟随，并且**取整** ——
像素画游戏里相机的亚像素移动会让砖缝疯狂闪烁，这是必须遵守的约束。

### 病根 B：每帧上万次 fillRect

```js
// v4.0 的 blitPX：对每个实体、每一帧、逐个像素画
for (y...) for (x...) { ctx.fillStyle = c; ctx.fillRect(...); }
```

一个 24×28 的精灵最多 672 次 `fillRect`，场上十五个实体 = **每帧上万次**。

修法两层：
1. 所有精灵预烤成离屏 canvas，运行时**每个实体一次 `drawImage`**
2. 精灵画布统一 **32×32，与瓦片 1:1**，按 dpr 预烤 ——
   像素网格对齐后，就近采样不会出现"有的像素 1px 有的 2px"的脏边

顺带抓到三个隐藏开销：

| 问题 | 修法 |
|---|---|
| 每帧贴整张 1440×1120 世界层（600 万像素） | 只贴可视区域；地形 + AO + 记忆压暗**烘焙**成世界层，只在状态变化时重建 |
| 小地图每帧重画 1575 个格子 | 只在玩家移动时重建 |
| 界面每 66ms 重建 40 格 + 12 行属性 + 5 槽位 | 改成动作驱动（回合制状态只在动作后变化） |

> **教训：用户说的"卡"和 profiler 上的"卡"经常不是一回事。
> 先问"是哪里不流畅"，再去看性能计数器。**

## 2. 动作设计

插值解决"移动"，但静止时角色还是一张纸片。补上：

- **三朝向**（正面 / 背面 / 侧面），侧面靠水平镜像复用
- **两帧行走**（双腿交替）+ 行走时的竖直起伏
- **攻击前倾**：走进敌人格时朝目标做一个小前冲（sin 包络 + 指数衰减）
- **怪物呼吸挤压**：`scale(1-sin·0.035, 1+sin·0.045)`，一点点形变就足够"活"
- **受击回弹**：朝玩家反方向弹开，配合白色闪光
- **脚下涟漪**：站在水里时扩散的水环

武器仍按 `cls.weapon` 分支绘制，所以"法师拿木桶"在数据结构上不可能发生。

---

## 3. 背包：为什么是整屏界面 + 手写拖拽

原来的侧栏是 5×4 = 20 个 **25px** 的小格子。两个问题：

1. 25px 装不下图标，也**拖不准**
2. 20 格对"五槽位 + 五档品质"的掉落节奏来说太小

改成整屏界面（左侧角色 + 5 装备槽，右侧 40 格网格，底部出售区），格子放大到 52px。

**拖拽用指针事件手写，没有用 HTML5 Drag & Drop**，原因：

- 原生 DnD 在 `file://` 和 WebView2 里的行为不一致
- 原生拖影无法自定义（这里需要显示品质色描边的拖影）
- 原生 DnD 在嵌套元素上的命中判定很别扭

手写版本：`mousedown` 记来源 → 生成跟手的 ghost → `mousemove` 用
`elementFromPoint` 找落点并高亮 → `mouseup` 执行。约 120 行，行为完全可控。

## 4. 商店：规则只有一个归属地

第一版我把"必须站在潮汐商栈上才能买"写在了 UI 的点击处理里，
模型层的 `buyItem()` 可以在任何地方买。

后果不是"玩家能作弊"，而是更隐蔽的：**模拟器里的 AI 把它当成了无限自动补给站**，
平衡数据直接失真。

修法：把地点判断移进 `buyItem()` 本身。UI 里保留同一判断只是为了给玩家即时反馈。

> **教训：规则只有一个执行点，而且必须在模型里。
> UI 里出现的同一规则，只能是提示，不能是守门。**

### 无套利约束

出售价和商店定价都从**同一个 `itemValue()`** 派生（×0.35 / ×1.75）。
因为只有一个来源，`买价 > 卖价` 恒成立。这一条还写进了冒烟测试：
**随机生成 60 件装备，逐件断言 `buyPrice > sellPrice`** ——
否则"买回来再卖出去"就是无限刷钱漏洞。

## 5. 这一轮的六个坑

### 坑 1：双引号开头、单引号结尾，吞掉了后面几十行

```js
this._log('...回复 ' + heal + " 点生命。', 'good');
//                               ↑ 这里本应是单引号
```

字符串一直延伸到下一个 `"`，中间所有代码变成字符串字面量，
表现是 `core.js` 整个模块加载失败。**但排查花了很久**，因为 `file://` 下
浏览器把脚本错误掩码成 `Script error.`，集成测试只报"模块未加载"这个二手现象。

于是补了 `tools/loadcheck.html`：同步 XHR 读源文件 + `new Function` 解析，
直接报出**哪个文件、哪一行**。（写这个工具时第一次跑也失败了 ——
`mark()` 定义在最后一个 `<script>` 块里，而函数声明只在**自己的脚本块内**提升。）

### 坑 2：坏目标黑名单的键不匹配

写入时用 `chest ? T.CHEST : T.FOUNTAIN`（漏了 shop 分支），
查询时用 `'chest' / 'fountain' / 'shop'`。商店失败被记成了泉水的键，
于是**无限重试同一个走不到的商栈** → 两格横跳 → 14/600 局卡死。

修法：键的生成收敛到 `_badKey(kind, x, y)` 一个函数，写入和查询共用。

### 坑 3：目标失效条件写得太宽

"满血时放弃宝箱目标"写成了对所有非敌人目标生效。
结果满血时每轮都判定目标失效、每轮重新选"最近的宝箱"，
而"最近"随位置变化 → 又是两格横跳（2/600 局）。
收窄到只对 `fountain` 生效即解决。

> **这是同一个 bug 的第三次出现**（前两次见 v9 的坑 2、坑 3）。
> 通用形态：**某个"每帧都可能翻转的判断"参与了目标选择，
> 而目标选择又会影响这个判断的输入。**
> 解法只有一个 —— 承诺 + 失效条件，且失效条件必须尽可能窄。

### 坑 4：测试不可复现

"画面最亮 15% 的平均亮度"在两次运行间从 **25.3** 跳到 **79.2**。
看着像回归，其实只是 `start()` 没传种子，开局地图不同。
固定 seed 后连跑两次数值逐位一致。

**不可复现的测试等于没有测试** —— 它只能告诉你"有事发生"。

### 坑 5：地形枚举里的死代码

`T.DOOR` 从没被任何生成逻辑写过，但渲染层和测试里都留着分支。
删掉并重排枚举值（`SHOP` 从 10 变成 9）—— 枚举值不持久化，重排是安全的。

### 坑 6：AI 需要"会花钱"

金币只进不出，模型里它就只是个装饰。所以给 AI 加了消费行为：
钱攒到 140 就去最近的商栈，到了就买升级 / 买圣水 / 清背包。
**经济系统因此也一起被验证了** —— 定价失衡会立刻反映到通关率上。

## v10.2 — 悬停详情、目录重构，以及工具链自己挖的坑

### 1. 上一轮的「document 级委托」其实是一次空转

上一轮把装备悬停从「每个面板各挂一个 mousemove」改成「整份文档挂一个委托」，
注释写得很漂亮，代码也在。**但它从来没有生效过**：

| 环节 | 应有状态 | 实际状态 |
|---|---|---|
| `bindTips()` | 在 `TideUI.init()` 里被调用 | 定义了，**没有任何人调用** |
| 渲染层元素 | 带 `data-tip="item" data-kind="bag" …` | 一个 `data-tip` 都没写 |
| `resolveTip()` | 从 `dataset` 还原出物品 | 永远拿不到入口 |
| 旧的面板 mousemove | 已删除 | **还在**，而且是唯一在干活的东西 |

于是就有了那个看起来很矛盾的反馈：「功能代码里有，但玩家看不见细节」——
玩家看到的是六个各管一段的监听器拼出来的提示，不是一个统一机制。

最值得记的一点：**这种"替换式重构"天然会骗过测试。**
只要新路径是死的、旧路径还在，一切照常工作：语法自检绿、74 项冒烟全绿、
拖拽与出售全都对。所以「重构完成」必须配一条**能失败的断言**。现在冒烟里有三条专盯它：

- `document.querySelectorAll('[data-tip]').length >= 8`（属性真的写进 DOM 了吗）
- 侧栏属性行悬停（旧代码里**根本没有**这一个监听器 → 只有委托生效才会亮）
- 出售区悬停（同上）

后两条是特意从旧实现里挑出来的「孤儿位置」——
**用旧代码覆盖不到的地方去证明新代码在工作**，比断言「某个地方还能弹气泡」有效得多。

顺带把内容加厚：空槽位也给一张卡（告诉玩家这个槽位装什么、怎么装），
商店卡片也显示与身上那件的逐项差值（买不买，判断依据就是这份差值）。

### 2. 一个被静默丢弃的函数参数

`itemTooltip(item, game, opts)` 的第三个参数是 `opts` 对象，
但旧的四处调用往里传的是**一个 HTML 字符串**（想加一行"售价 xx 金币"）：

```js
tooltip(itemTooltip(it, g, '<div class="tt-cmp">…</div>'), ev);   // 旧写法
```

字符串上没有 `opts.price`，于是那段 HTML 被无声无息地丢掉，
只有 `itemTooltip` 自己产出的身价行在凑数 —— 界面看起来"对"，所以一直没人发现。
**位置参数是最容易被传错的东西**，而且传错了不会报错。这次让它真的收 `opts`。

### 3. 目录重构：把启动器搬到最外层

玩家的原话是「我要找好久才能找到现在的游戏启动器」。重构后的形态：

```
numeral-tide/                    ← 整个文件夹拷走，双击即玩
├─ 数值潮汐.exe                  ← 启动器就在最表层
├─ 3 个 WebView2 DLL
├─ www/                          ← 游戏本体（构建产物，来自 src/）
├─ 说明.txt
├─ release/数值潮汐/             ← 干净分发包（+ .zip）
├─ 旧版-数字吞噬/index.html       ← 最初的单文件原型，独立保留
├─ 数值潮汐/（src/  tools/  launcher/  builder/  assets-raw/  release/  www/）
└─ README.md  CHANGELOG.md  LICENSE  开发记录/
```

三条取舍：

1. **可运行文件放项目根**，启动器双击距离最短；
2. **源码分开住**，一眼分清"能玩的"和"能改的"；
3. **最初的单文件原型独立成 `旧版-数字吞噬/`** —— 它是一个完整可玩的对照物，
   不是历史垃圾：判断"系统是不是加过头了"的时候，回头看这个文件最清楚。

代价必须说清楚：**项目根不再是纯源码树**。而旧版 `build.ps1` 里有一行
`Remove-Item $dist -Recurse -Force`，其中 `$dist` 是个变量 ——
"把输出改到项目根"这个需求恰好就在推着人踩上去。所以新版脚本：

- 清理目标写成**白名单字面量**，不是"输出目录"这种推导值；
- 每次删除前过 `Assert-InRoot`：必须**在项目根之内**、且**不等于项目根本身**；
- 构建前先确认"这里确实是本项目的根"（存在 `src\index.html`）。

> 原则：**删除动作永远不要作用于由变量推导出来的目录。**

### 4. 工具链自己挖的两个坑（比游戏 bug 更要命）

这一轮真正的损失不在游戏里，而在**改文件的工具**上：

**(a) 改写更短的内容时，文件没有被截断。**
`ui.js` 被改短之后，末尾残留了上一版的 446 字符（一个残缺的导出对象），
文件变成「正确内容 + 一段旧尾巴」，表现是**整份模块无法解析**。

**(b) 同一批里发起的多个编辑会互相覆盖。**
冒烟脚本里新加的测试块根本没写进文件，工具却回了"成功"。

两个坑的共性：**静默**。它们不报错、不留痕，只是安静地把成果丢掉，
而人还以为什么都好了。这一轮因此多花了好几个来回，也催生了三样东西：

| 新增 | 作用 |
|---|---|
| `tools/syncline.html` | 语法错误**行号**定位（loadcheck 只给文件名，且 V8 对 `new Function` 不给行号） |
| 编辑后逐条机器审计 | 每处改动都要能被机器验证，不能靠"工具说成功了" |
| 一次只改一处、改完立即验证 | 批处理带来的并行风险不值得省那几个来回 |

`syncline.html` 的原理值得单独记：把源文件包成 **Blob 外链脚本**塞进页面，
浏览器解析外链脚本失败时 `window.onerror` 会带回精确的 **行:列**，
而且同源 blob 不会被掩码成 `Script error.`。它一上来就把故障点定到了第 934 行。

### 5. 平衡：休闲 94.5% → 89.0%，只动一个键

休闲 94.5% 偏高，但"偏高"不能靠感觉调。先用新写的 `tools/sim_tune.html`
做**单变量扫描**（只改内存里的配置对象，源码一行不动，扫完即忘）：

| `casual.healAfterWin` | 通关率 | 平均回合 | 平均击杀 |
|---|---|---|---|
| 0.120（原值） | 94.0% | 320.7 | 51.5 |
| 0.100 | 90.7% | 315.0 | 48.6 |
| **0.080（新值）** | **87.3%** | 311.8 | 47.0 |
| 0.060 | 83.3% | 316.2 | 47.3 |

选「战后回血」当旋钮、而不是"把敌人改强"，理由是**它加强的是这个游戏的核心张力**：
HP 是唯一的稀缺资源，回血一多，"绕开谁、先打谁、值不值得绕去泉水"这些决策就全失效了。
把敌人调强只是把回合拉长，不会让玩家多做决定。

改完跑满 600 局（每档 200，固定种子 1000）复核：

| 难度 | 通关率 | 平均回合 | 平均击杀 | 结局 |
|---|---|---|---|---|
| 休闲 | **89.0%** | 318.3 | 48.0 | win 178 / dead 22 |
| 标准 | 60.5%（未变） | 305.6 | 60.3 | win 121 / dead 79 |
| 深渊 | 36.5%（未变） | 310.2 | 107.9 | win 73 / dead 127 |

`stall = 0`、`timeout = 0`，失败只剩 `dead`。
**另外两档一个点都没动** —— 这正是单变量扫描想要的证据：改的是休闲，动的就只有休闲。

武器偏好也顺带看了一眼：休闲/标准/深渊三档里，秘藏选取分布都很平
（最高 149 / 最低 1，最低那几个是 `gambler`、`batfang` 这类高风险选项），
没有出现"某一档只有一个正确答案"的塌缩。

## v10.3 — 元凶抓到了：地形层漏掉了一个 `−cam`

### 玩家报的现象（原话）

> 「人物不能固定在画面中间。地图是黑色的，但也有正常的，随着人物移动，
> 正常的地图也会移动，好不容易走到地图显示正常的地方，人物移动又错位了，
> 正常的只是恰好而已。」

翻成技术语言：**地形与玩家之间有一个随相机变化的偏移**，
而且这个偏移在相机停在某些位置时会恰好抵消。

### 代码里只有一处不符合约定

渲染层有一个贯穿全局的坐标约定：**屏幕坐标 = 世界坐标 − 相机**。
全项目所有绘制点都遵守它，只有世界地形层这一处不是：

| 位置 | 代码 | 是否遵守约定 |
|---|---|---|
| 动画地形 | `const dx = x * TILE - camX` | 是 |
| 玩家 | `const dx = vis.px * TILE - camX` | 是 |
| 敌人 | `const dx = v.x * TILE - camX` | 是 |
| 粒子/飘字 | `cut((x * TILE + TILE / 2 - camX) * dpr, …)` | 是 |
| **世界地形层** | `drawImage(worldCv, sx0*dpr, sy0*dpr, …, **sx0, sy0**, …)` | **否** |

地形层是从烘焙好的离屏画布上"挖一块"贴到屏幕上。
挖的**源**矩形起点是 `(sx0, sy0) = (max(0,camX), max(0,camY))`，
而贴的**目标**位置也写成了 `(sx0, sy0)` —— 把源偏移当成了目标偏移。

后果：相机滚到 `(camX, camY)` 时，地形仍然被画在「世界坐标 = 屏幕坐标」的位置上，
于是

- 地形与玩家/敌人**错开整整一个相机位移**（玩家看起来"没站在地图上"）；
- 视口左上留出一条宽度等于 `camX` / `camY` 的**纯黑带**（因为那块从没被画过）；
- 而相机停在 `(0,0)`（地图左上角）时这个错误**恰好抵消** ——
  所以"走到某个地方就又正常了"。

修法只有 4 个字符：目标坐标改成 `(sx0 - camX, sy0 - camY)`。

### 为什么它能活这么久（这才是真正值得记的部分）

1. **不报错、不崩、不抛异常。** 只是两个字面量写错。
2. **像素统计抓不到。** 那一版冒烟测试检查的是"平均亮度""色块种类""对比度"——
   地形整体平移 300px 完全不影响这些指标。
3. **视觉校验也没抓住。** 早期截图取景时相机停在 `(16,0)`，
   错位只有 16px，混在像素画里看不出来。
4. **它伪装成偶发故障。** 相机回原点时自愈，于是最容易被归因成
   "缓存""显卡""偶发 bug"。

### 教训：这类 bug 需要专门构造的判据

**"看起来正常"不是一个可判定的条件，"某个不变量成立"才是。**
这里的不变量是：*相机滚到地图中部时，视口四边都必须被地形铺满*。
于是新增了 `tools/probe_cam.html`（取证）与冒烟第 21 条（回归）：

- 把玩家挪到地图正中（位移 > 400px 会触发相机瞬移，不必等平滑收敛）；
- 强制全图已探索 —— **把"迷雾本来就是黑的"这个干扰项排除掉**，
  否则空白带与正常迷雾无法区分；
- 读回画布像素，统计"整列/整行都是纯填充色"的空白带宽度，必须 ≈ 0；
- **并且断言相机确实滚起来了**。相机没滚动时这条测试是空转的，
  而空转的测试比没有测试更危险 —— 它会给出虚假的安全感。

修复前后由同一个工具测得：

| 相机 | 左空白带 | 上空白带 | 结论 |
|---|---|---|---|
| `(310, 101)` 修复前 | 266 px | **101 px（恰好等于 camY）** | 错位 |
| `(311, 100)` 修复后 | **0 px** | **0 px** | 正确 |

上空白带恰好等于 `camY`，这就是"漏掉一个 `−cam`"的指纹。

### 顺带的收获：把"取证"和"测试"分开

`probe_cam.html` 不做断言、只打印事实（相机、玩家应有的屏幕位置、
四边空白带宽度、一张 54×22 的 ASCII 亮度图）。
它存在的意义是：**在写断言之前先看清现象**。
如果一上手就写断言，很容易写出一个"永远为真"的断言，
然后拿它当证据去修一个不存在的问题。

## v10.4 — 层级梯子、魂技、融合，以及「敌人变强并不会让游戏变难」

### 1. 玩家报的 bug：气泡被背包挡住了

> 「打开背包发现装备的详情在背包界面后面。」

查下去发现不是某一处写错，而是**根本没有层级梯子** —— 每个 z-index 都是各自就事论事定的：

| 元素 | 原值 | 问题 |
|---|---|---|
| `#enemy-info` | 88 | ok |
| `#tooltip` | **90** | < 背包 96 → 被背包盖住（玩家报的） |
| `#toast` | **95** | < 背包 96 / 弹窗 100 → **在背包里操作失败时那句提示根本看不见** |
| `#inv-screen` | 96 | ok |
| `.modal` | 100 | ok |
| `.drag-ghost` | 200 | ok |

第二个问题玩家还没遇到 —— 因为在背包里拖错槽位时那句「不能装在「武器」」根本没法显示，
所以也就没人知道它被吞了。**一个根因两个症状，其中一个不可见。**

改法是把梯子写进 CSS 顶部当权威（气泡 240 / 提示条 300），
并加一条冒烟断言。关键在这条断言断言的是**关系**而不是数字：

```js
if (!(zTip > zInv)) fail('悬停气泡在背包之下…');
if (!(zToast > zInv && zToast > zModal)) fail('提示条在背包/弹窗之下…');
```

散落的魔数之间没有"关系"可言，所以只断言某个具体数字毫无意义 ——
下次有人把背包调到 101，测试照样绿。**断言关系，才能锁住设计意图。**

顺带踩到一个测试自身的坑：`.drag-ghost` 只在拖拽过程中存在，
平时 `querySelector` 拿到 null → 层级检查报了 `NaN`。
修法是临时造一个同 class 的元素来量规则，而不是"查不到就跳过" ——
跳过等于把这条规则排除在保护之外。

### 2. 魂技：把「时机」做成一个按钮（设计取自《元气骑士》）

元气骑士里最提气的一环是每个角色有自己的技能。移植时最容易走偏的是把它做成
"伤害更高一点"，那样只是数值，不是玩法。所以四个技能**各自换掉一种压力**：

| 技能 | 换掉的是 | 关键设计 |
|---|---|---|
| 裂地斩 | 被贴身时的走位压力 | **不吃反击** —— 改变的是"你敢不敢站进去"，不是"你打得多疼" |
| 潮语洪流 | 距离压力 | 隔着半个房间先手削一刀，让"在哪开战"变成可选 |
| 疾影 | 回合压力 | 免费行动不推进潮汐、敌人也不动 |
| 不退之壁 | 血量压力 | 残血时硬顶三回合，给"要不要撤"加一个新选项 |

工程上有三条经验：

1. **规则只写在模型层。** `core.useSkill()` 是唯一入口，HUD 按钮、快捷键 Q、
   模拟器 AI 全都调它。把"能不能放"写进界面是上一轮踩过的坑 ——
   模拟器的 AI 会绕过规则，于是平衡数据是假的。
2. **空放不消耗冷却。** 范围里没目标时失败，且 `skillCd` 保持不变。
   技能类设计的挫败感几乎都来自"按了没反应"，而玩家分不清"没反应"和"还在冷却"。
   这条有专门的测试。
3. **免费行动需要一个新的收口。** 原来"动作结束 → 推进回合"散在 4 个地方，
   加了免费行动就必须收敛成一个 `_afterAction()`，否则迟早漏一处。
   同时模拟器的卡死判据也得改：`行动了但回合没推进` 过去一律算卡死，
   现在只有**没有免费次数时**才算 —— 否则新机制一上线，
   模拟器就会把正常的技能使用误报成死锁。

还有一条最容易漏的：**AI 不会用 = 机制在平衡数据里不存在**。
所以测试里直接断言 `playHeadless()` 跑完一局后 `skillUses > 0`。

### 3. 融合：定价错一次，整个平衡就崩了（设计取自《元气骑士》的武器融合）

把一件拖到同品质的另一件上 → 合成高一档，走"材料 + 金币"。

定价我一开始只考虑了一条约束（**必须 ≥ 结果售价**，否则「融合→出售」是净赚回路），
于是 `fuseRate = 0.40`。结果一跑模拟：

| 指标 | 加融合前 | fuseRate 0.40 | fuseRate 0.90（现在） |
|---|---|---|---|
| 标准难度通关率 | 60.5% | **79%** | 61.5% |
| 掉落里的史诗 | 412 | 1735 | 445 |
| 掉落里的传说 | 207 | 436 | 254 |

漏掉的第二条约束是**必须和商店价可比**：0.40 时一件传说只要 58 金币，
而商店卖同款要 256 —— 融合于是变成"无脑变强"的按钮。
`fuseRate = 0.90` 仍然比商店便宜（材料毕竟得自己出），但不是免费午餐。

> 教训：**反套利只保证了"不会刷钱"，没保证"不会通胀"。**
> 定价要同时对齐三个锚点：材料的售价、商店价、以及"玩家拿到它应该付出多少游戏时间"。

测试上，除了一条针对融合的反套利扫描（随机 60 组，融合费均 ≥ 产物售价），
还加了一条"AI 会不会真的去融合"—— 和魂技同理。

### 4. 反直觉发现：提高敌人强度几乎不降低通关率

加完两个新机制后通关率飙升（标准 60.5% → 79%）。第一反应是"敌人太弱了"，
于是扫 `standard.enemyMul`：

| enemyMul | 1.00 | 1.25 | 1.50 | 1.75 |
|---|---|---|---|---|
| 通关率 | 82.5% | 74.2% | 80.8% | 78.3% |
| 平均回合 | 352 | 356 | 400 | 402 |
| 平均击杀 | 74 | 89 | 120 | 136 |

**基本持平，甚至非单调。** 原因是这个循环：

```
敌人更强 → 击杀更多 → 升级更快 + 掉落更多 → 玩家同步变强 → 通关率不变
```

回合数从 352 涨到 402、击杀从 74 涨到 136 —— 敌人强度改变的是**节奏**，不是**难度**。
在"击杀驱动成长"的循环里，它根本不是难度旋钮。

真正的难度旋钮是**战后回血**，因为它直接决定「HP 还算不算稀缺资源」：

| 难度 | 基准 | 候选值 → 通关率 | 定稿 |
|---|---|---|---|
| 休闲 | 0.08 → 97% | 0.06 → 93%｜**0.04 → 87%**｜0.02 → 82% | **0.040** |
| 标准 | 0.07 → 82.5% | 0.045 → 65.8%｜0.02 → 45%｜0 → 28.3% | **0.040** |
| 深渊 | 0.045 → 61% | **0.03 → 40%**｜0.015 → 23%｜0 → 13% | **0.028** |

注意标准难度：为了抵消新机制带来的 +22 个百分点，回血要从 0.07 砍到 0.04。
这不是"把新东西削弱"，而是**让新工具变成必需品** —— 有了魂技和融合才顶得住这个难度。

### 5. 稳定性：绿色版跑在别人机器上

这一版加了两处兜底，理由是发行形态本身：

- **全局错误网**：未捕获异常会让 rAF 循环停掉，玩家看到的是一张静止的黑屏，
  分不清"游戏坏了""还在加载"还是"我按错了"。现在给一句人话 + 一个「重新开始」按钮。
- **画布上下文兜底**：WebView2 在显卡驱动异常 / 硬件加速被关掉时，
  `getContext('2d')` 可能返回 null。原代码会**每帧抛一次错**（黑屏 + 控制台刷屏）。
  现在在这种情况下直接停下并解释原因（顺带告诉玩家可以关掉硬件加速）。

另外把"新界面有没有挤坏布局"做成了断言（HUD 按钮区不得溢出舞台、
侧栏魂技卡必须真的渲染出来）。这类问题以前只能靠截图肉眼看，
而截图这条链在当前环境里不稳定（`--window-size` + `--virtual-time-budget` 组合下
根本不生成文件），DOM 几何反而是可靠且永久的判据。

### 6. 定稿数据（600 局，固定种子）

| 难度 | 通关率 | 平均回合 | 平均击杀 | 目标 |
|---|---|---|---|---|
| 休闲 | **87.5%** | 293.7 | 46.7 | 最轻松的一档，但要有代价 |
| 标准 | **61.5%** | 298.9 | 60.9 | 保持 v10 基准 60.5% 不变 |
| 深渊 | **39.0%** | 292.8 | 108.2 | 保持 v10 基准 36.5% 附近 |

`stall = 0`、`timeout = 0`，失败只剩 `dead`；
死亡分布分散在巨兽 / 镜影 / 幽魂 / 潮水等多个来源，没有单一"必死卡点"。

## v10.5 — 兜底自己成了最大的 bug，以及"有感觉"要能被测量

玩家的三条反馈：

> ①「开始时会弹出错误，无法开启游戏，特别是切换角色时」
> ②「融合功能可以，但没有弹出东西」
> ③「技能没有任何感觉，虽然有效」

三条的性质完全不同：①是我自己引入的故障，②是事件队列没被消费，③是表现层缺失。
但三条共享同一个教训 —— **"逻辑正确"和"体验正确"之间隔着一整层没人检查的东西。**

### 1. 兜底反噬：一个无害的错误就能锁死整个游戏

上一轮我加了"全局错误网"：任何未捕获错误 → **全屏覆盖 + 停掉 rAF**。
它有个我没想到的前提：假定"任何 window 上的 error 事件 = 游戏已经崩了"。

现实是，浏览器还会在 window 上报**资源加载失败**（这类事件没有 message，
只有 target）—— 页面里任何一个 404 都能触发。于是：

```
一个 404  →  error 事件  →  全屏停机浮层  →  玩家："开始时就弹出错误，无法开启游戏"
```

更糟的是它**会自我放大**：错够 5 次就永久停机，
而"每帧抛错"的地方（比如下面那条装饰背景）一秒内就能抛满 5 次。

改法是把兜底**分级**：

| 情况 | 处理 | 理由 |
|---|---|---|
| 资源加载失败（无 message / error） | **完全忽略** | 一个 404 不该有能力弄坏游戏 |
| 单个真 JS 错误 | 左下角一条会自己消失的提示，**不停机** | 先让玩家能继续玩，比什么都重要 |
| 12 秒内 ≥ 5 次真错误 | 才升级为全屏停机（带「复制错误信息」） | 这才是"真的崩了" |

同时加了三条冒烟断言把这件事钉住：资源型错误必须被忽略、单个真错误不许停机、
连续出错才允许停机。**"兜底"本身也是要写测试的功能** —— 这一条的代价我付了一整轮。

### 2. 装饰不该有能力弄坏游戏

顺着"什么样的代码会每帧抛错"去找，找到了标题页的动态潮汐背景（`ui.js`）：

```js
const c = cv.getContext('2d');     // ← 没有判空
function frame() { c.createLinearGradient(...); ... requestAnimationFrame(frame); }
```

`getContext('2d')` 在 WebView2 里可能因为显卡驱动抖动 / 硬件加速被关而返回 null，
而这段代码**每帧**都在用 `c`。配上第一节那个"错 5 次就停机"的兜底，
表现就是"一开局就弹错、进不去游戏"，而且换个时间重开又会好 ——
完全符合玩家描述的"有时能开、特别是切换角色时"。

修法写进了注释当原则：**装饰不该有能力弄坏游戏。**
拿不到上下文就直接不画；画的过程中出错就安静地停掉这个循环。
顺带补了 `cv.width/height` 的最小值（容器没布局时可能是 0/NaN，
而 `createLinearGradient` 拿到非有限值会直接抛错）。

> 排查过程也值得记：file:// 与 http、dpr = 1 / 1.25 / 1.5、源码与发行版副本，
> **六种组合全部复现不出来**。当复现不了的时候，正确的动作不是继续猜，
> 而是换目标：先让"玩家能继续玩"变成结构性的保证
> （不停机兜底 + 错误写进 localStorage + 复制按钮），
> 再把最可能的"每帧抛错"点逐一封死。玩家描述的现象是"进不去"，
> 那就先让"进不去"变成不可能。

### 3. 融合"没有弹出东西"：事件队列没人消费

`fuseItems()` 会 push 一个 `kind: 'fuse'` 事件，主循环里也确实有对应的音效 + 提示条。
但**融合的入口在背包界面**，而背包的收尾函数只调了 `TideMain.refresh()`（重画 DOM），
**没有消费事件队列** —— 于是事件堆在那里，音效和提示条全都不出现。

```
模型 push 事件  →  谁来消费？  → 主循环（走路、攻击、技能都走这里）
                                 ↑ 但背包/商店的操作从不经过主循环
```

修法是给 `TideMain` 加一个 `flush()`（= 消费一次事件队列），
背包的收尾走它。教训是架构层面的：**在事件驱动的结构里，
"谁来消费队列"必须有唯一的归属，否则每加一个新入口就会静默地少一层反馈。**

还补了一个纯界面的反馈：融合产物落在背包末尾，玩家合完会立刻去找"刚那件在哪"，
所以给它加了一次跳一下的高亮（`just-made`）—— 只弹一句 toast 是不够的。

### 4. "技能没有感觉"：把主观描述翻译成可测量的量

玩家说"虽然有效，但没有任何感觉"。第一件事是量它，于是给特效层加了观测接口：

```js
TideFX.counts()  →  { parts, texts, rings, streaks, shake }
```

实测（放一次不退之壁）：

| | 粒子 | 飘字 | 形状特效 | 震屏 |
|---|---|---|---|---|
| 修复前 | **0** | **0** | — | 3.44 |
| 修复后 | 24 | 1 | 2 环 | 4.0 |

只有震屏 —— 也就是说玩家放技能时，画面上**除了屏幕抖一下什么都没有**。
难怪"没感觉"。

补的四层（缺一层都会觉得缺）：

| 层 | 内容 | 为什么不能省 |
|---|---|---|
| 音 | 四个技能各一个音色 | 听觉比视觉更容易被记住 |
| 动作 | 身体上浮 + 地面法阵 + 身上一层光 | 这个动作属于**玩家自己**，确认感最强 |
| 特效 | 每个技能一个**招牌形状** | 见下 |
| 界面 | 技能键脉冲一下 | "你按的那一下被收到了" |

关于"招牌形状"，这是移植《元气骑士》技能时最容易漏的一点：
如果四个技能都只放一圈通用粒子，玩家记忆里只会留下"放了技能"，
而不是"放了裂地斩"。**形状是最好记的语言**：

- 裂地斩 → **贴着地面的冲击环**（地裂）
- 潮语洪流 → **打出去的能量束**（水束）
- 疾影 → **身后的残影拖尾**
- 不退之壁 → **包住人的护盾罩**，而且只要增益还在就**一直亮着**

最后一条尤其重要：持续型增益必须一直看得见。技能价值的一半是
"我知道它还在生效" —— 只闪一下的护盾会让玩家怀疑自己是不是白点了。

为了让这四层可回归，冒烟新增了 5 条断言，直接断言**数量**：

```
ok  裂地斩有感觉：74 粒子 / 2 冲击环 / 9 条飘字 / 施法姿态已触发
ok  潮语洪流有感觉：26 粒子 / 1 道水束 / 3 条飘字
ok  疾影有感觉：18 粒子 / 5 道残影 / 1 条飘字
ok  不退之壁有感觉：24 粒子 / 2 环 / 增益持续 2 回合（护盾罩随增益存在）
```

顺带新增了 `tools/probe_err.html`：模拟玩家的手指走一遍
「切换角色 → 切换难度 → 开始下潜 → 放技能 → 返回标题再开一局」，
把全过程所有未捕获错误抓下来（含文件与行号）。
它的存在理由很直接：**集成冒烟是自己调 API 开局的，走不到标题页那条路径** ——
所以它在冒烟里全绿，在玩家手里一按就炸。

## v10.6 —— 把「四个角色的技能」真正做完

这一轮的起点是"技能没感觉"的后续：要"做加法，但逻辑要完整"。做完的结论有点意外：
**四个技能的机制、姿态、特效、音色、界面，其实早就全在了；真正坏掉的是测试脚手架。**

### 1. 脚手架的两种坏法（比游戏 bug 更危险）

因为坏的是测试本身，所以它**不会报错，只会静默地什么都不验**。

**① 结构坏了 —— `ok = 0`**
`smoke.html` 的震晕测试段落重写时少了一个 `}`：`else {` 没有闭合，
紧跟的 `} catch` 被 `try` 抢走。整个 `<script>` 因此**解析失败**，
页面显示 `ok = 0`。注意这个数字的含义：不是"测试不通过"，而是**"测试根本没跑"**。

> 教训：**`ok = 0` 和 `ok = 108` 是两种不同的故障，不要去调断言。**
> 先看脚本有没有跑起来（`loadcheck.html` 只查源文件的语法，
> 它查不到测试脚手架自身的语法 —— 这是一个盲区，本期才暴露）。

**② 判据坏了 —— 假失败**
剩下那 1 条 `被震晕的敌人还是出手了` 是**断言写错**，机制是对的：
`_skillHit`（我打它）和 `enemyHit`（它打我）**都推 `kind:'hit'`**，
技能命中多带一个 `skill:true`。原判据没排除自己那一下，于是"技能命中"被当成"敌人反击"。

```js
// 改前：任何打在这个敌人身上的 'hit' 都算它出手了
if (evsS[qi].kind === 'hit' && evsS[qi].enemy === eS) attacked = true;
// 改后：只认不是技能造成的那一下
if (evsS[qi].kind === 'hit' && evsS[qi].enemy === eS && !evsS[qi].skill) attacked = true;
```

顺手把断言从"看残留的 `stun` 回合数"换成"看 `stunned` 事件有没有发生" ——
残留回合数会随 `endTurn` 的结算顺序变化，而"那一次行动到底有没有被跳过"才是语义。

### 2. 顺手抓到的两个实质缺陷

**① 面板文案在骗玩家（真问题）**
`endTurn` 里状态递减发生在**施放的那一回合**，可那一手已经消耗掉了整个回合。后果：

| 技能 | 面板写 | 实际 |
|---|---|---|
| 潮语洪流 | 潮湿 2 回合 | **1 回合**（术士的核心联动被砍半） |
| 不退之壁 | 双防 3 回合 | **2 回合** |

修法是在 `endTurn` 里加**一条统一规则**：*出生那一回合不倒计时*（给状态盖 `birth` 戳）。

> **刻意不改冷却**：冷却是在"下一次想放"的那一刻结算的，原口径本来就对
> （cd=10 → 真的等 10 个回合）。把它一起"修正"反而会多等一等。
> 一条规则套两个语义不同的东西，就是下一次故障的种子。

改动落在 `_pushBuff`（玩家增益）与 `useSkill` 的潮湿（敌人状态）两处，
`endTurn` 里用同一个 `born` 变量消费。

**② 击退会斜着推（防御性修正，不改平衡）**
`_knockback` 原本对 x/y 各取一次 `sign`，是**斜推**。
但要说实话：裂地斩 `radius:1` 只覆盖正交格，
**斜位根本进不了技能范围，这条路径实际走不到**。
所以这次改成"只沿主轴推"**不影响任何平衡数据**，价值在于：
将来若加长距离击退，怪不会被扔到它自己走不进来的格子上（本作移动是四方向的）。
同时修了 `from` 字段（原本写的是终点）。

### 3. 两条工具链的坑（本期新发现）

**① 行号口径不统一 —— `Get-Content` 会少算**
同一个 `render.js`：`Select-String` 说 `get cast()` 在 724 行，
`(Get-Content render.js).Count` 说文件只有 676 行。

原因：文件里**混了行尾风格**（676 个 CRLF + 60 个裸 LF），
`Get-Content` 的口径和浏览器/`.NET StreamReader` 不一致 → 它把 60 行合并了。

> **铁律：按行号定位只用 `readFile` / `Select-String`，它们和浏览器一致。**
> 别用 `Get-Content` 的下标去推算行号 —— 之前 "编辑工具静默出错" 的迷雾，
> 有一部分其实是这个口径差造成的（我按错误的行号看了错误的现场）。

**② `.NET` 静态方法的当前目录 ≠ PowerShell 的 `cd`**
`Set-Location` 到项目目录后，`[System.IO.File]::ReadAllText("docs\x.md")`
仍然去 `E:\LOBEHUB_work\docs\x.md` 找 —— PowerShell cmdlet 认相对路径，
.NET 静态方法认的是**进程工作目录**。

> **铁律：给 `.NET` 方法一律传绝对路径。**

| 项目 | 结果 |
|---|---|
| 冒烟测试 | 102 项 → **109 项全绿**（源码 + 分发包副本双跑） |

## v10.7 —— 元进度（潮汐结晶）与 BGM

两件计划了很久的事。共同点：它们都**很容易悄悄弄坏别的东西**，
所以这一轮真正的工作量不在"加功能"，而在"加一条结构上的隔离带"。

### 1. 元进度：把"污染平衡"这件事从自觉变成不可能

本作唯一的验收标准是模拟器跑出来的通关率。元进度如果默认生效，
通关率就不再是"这个版本的难度"，而变成"我解锁了多少" —— 基准数据直接作废，
而且**是无声作废**（没人会收到报错，只会觉得"这版好像简单了"）。

所以切了三层，各归各位：

| 层 | 位置 | 职责 |
|---|---|---|
| 数据层 | `data.js` 的 `META` | 解锁表 + 加成折算（**纯函数，无任何存储依赖**） |
| 存档层 | `meta.js`（新文件） | localStorage 读写、购买、结算入账 |
| 模型层 | `core.js` | **只在显式传入 `opts.meta` 时**才应用加成 |

模拟器从来不传 `opts.meta` → 天然拿不到元进度。
这条不靠自觉，靠结构；并且写成了冒烟里的一条硬断言：

```
ok  元进度不泄漏：不传 meta 的一局 金币 0 / 背包 40 / 生命 130（模拟器的基准仍然干净）
```

**验证**：加完元进度 + BGM 后重跑 200 局 ×3 档，数字与改动前**逐位相同**
（90% / 64.5% / 39.5%，连击杀数 45.3 / 64.7 / 113.2 都一模一样）。
逐位相同比"差不多"强得多 —— 它证明这批代码真的没碰到战斗逻辑。

### 2. 存档是不可信输入（这一轮抓到一个洞）

单机游戏的存档被手改是**玩法的一部分**，因此 `load()` 的职责不是"读出来"，
而是"读出来并保证它长得像一份合法存档"。

`sanitize()` 把负数、越界、类型错误全部就地修正。但第一版只做了
"id 是否存在于解锁表"这一层过滤，于是漏掉一个洞：

```
owned: { gift: 1 }     // 潮汐馈赠，前置是「祖传遗物」heirloom
→ 只有 gift 也照样生效 = 白拿稀有开局装备，绕开整条付费链
```

补法是让**已购集合对前置封闭**（反复收敛到不动点，因为前置还可能再套前置）：

```js
for (let pass = 0; pass <= M.unlocks.length; pass++) {
  let dropped = false;
  for (const id in out.owned) {
    const u = M.unlockById(id);
    if (u && u.req && !out.owned[u.req]) { delete out.owned[id]; dropped = true; }
  }
  if (!dropped) break;
}
```

> 这是"我写的断言把我自己写的代码抓了"的一个好例子。
> 当时第一条断言失败，第一反应是"断言写错了"，但想清楚之后发现
> **是代码错了**：既然选择钳制存档，就应该把一致性钳完整，而不是钳一半。

### 3. 结算必须幂等（不可逆的那类操作）

结算界面会被重绘、玩家会连点两次「再来一局」、死亡动画可能触发两次。
同一局的结晶结算两次 = 结晶凭空翻倍，而元进度翻倍是**不可逆的**（玩家已经花掉了）。

保护标记直接打在**这一局的 `game` 对象**上：

```js
if (!game._metaSettled) { game._metaSettled = true; /* 结算 */ }
```

为什么不用外部传入的 `runId`：`game` 对象天然是每局一个新的，
于是"幂等"不依赖调用方记得传 id —— 那种约定迟早会被漏掉。

### 4. 顺手收敛的一处技术债

背包容量原先在 **6 处**各自去读 `D.LOOT.backpackSize`。
加了"补给袋"这类局外加成之后，那种写法必然漏改一处，
而漏改的症状是"我买了补给袋，背包却还是满的" ——
从表面完全看不出是配置没读到。

现在收敛成唯一入口 `Game.bagCap()`（`ui.js` 也改走它）。
9 处替换用 Python 按字节改并**数数**，数量对不上就整份不写。

### 5. BGM：零音频文件，但有两件事比"好听"重要

全部用 Web Audio 现场合成（延续"一个文件夹带走"的约束）。

**① 不能用 `setInterval` 直接发声。**
定时器精度只有 ~15ms，还会被后台标签页节流到 1s —— 直接发声会一顿一顿。
用的是标准的**提前排程**：定时器每 25ms 醒一次，把未来 0.25 秒内该响的音符
按**绝对时间**交给音频时钟，由音频线程精确执行。主线程再卡也不走音。

**② 不发声的时候不能还在算。**
静音 / 失焦 / 不在游戏里 → **直接停掉定时器**，而不是把 master 增益拧到 0。
增益为 0 时振荡器仍在跑，笔记本的风扇会告诉你这件事。

音乐设计上只叠了低音 + 琶音 + 危机段落的浪声，铺底交给已有的 ambient 低鸣
（不重复造 pad）。音阶选 **A 小调五声**，因为它没有小二度，
程序怎么排列都不会难听；琶音走势**写死而不是随机** ——
随机每次都不一样，听起来像"没写完"，而且改动之后无法判断是变好还是变坏。

三段强度由**氛围**表达，不用提示条：

| 段落 | 触发 | 速度 |
|---|---|---|
| 静谧 | 标题页 | 72 |
| 探索 | 局内 | 92 |
| 危机 | 水位 ≥2 或血量 <35% | 108 |

> `music()` 会被渲染循环每帧调用，所以 `bgmApply()` **必须幂等** ——
> 一旦有副作用（比如每次把 `BGM.step` 归零），音乐就会卡在第 0 步反复重来。
> 这和"每帧可能翻转的判断参与目标选择"是同一类陷阱的第四次出现。

### 6. 工具链的坑（本轮新发现）

**Edge 进程会占住 user-data-dir。**
上一次的 Edge 没退干净时，新进程会把 URL **转交给已有实例后直接退出**，
于是 `--dump-dom` 输出**0 字节**、没有报错、看起来像页面坏了。
而它和"页面真的坏了"的现象完全一样。

> 对策：每次取证前先 `Stop-Process msedge -Force`，等 2~3 秒。
> 反过来也成立：看到 `--dump-dom` 输出 0 字节，**先怀疑进程，再怀疑代码**。

另外，`--user-data-dir` 指向一个**全新的**目录时，Edge 的首次运行流程会吞掉
`--dump-dom` 的输出（即使加了 `--no-first-run`）。复用已经跑过的 profile 目录最稳。

## v10.8 —— 「怎么卡住了」：一次把冒烟测试的盲区打出来的 bug

### 1. 玩家报的是"卡住"，实际是"按钮在屏幕外面"

v10.7 交付后，反馈是三个字：**「怎么卡住了」**。

真因是 v10.7 往标题页加了第三块「潮汐结晶」区块，把内容撑到 **1132px**，
而 exe 的窗口客户区只有 **880px**：

```
title-inner  clientH = 880   scrollH = 1132
「开始下潜」  top = 1003   bottom = 1051   ← 完全在可视区之外
```

玩家打开游戏，看到的是一个**看起来完整**的标题页 —— 但开始按钮在下面。
他没有任何理由去滚动一个看起来完整的页面，所以结论就是"卡住了"。

**而当时冒烟 126 项（当时 118 项）全绿。** 原因值得抄在本子上：

> **`element.click()` 不关心元素在不在屏幕里。**
> 程序化点击永远成功；真人用鼠标点，才需要它真的可见。
> 所以「按钮能不能点」这类断言，用 click 是**永远测不出来**的。

修法分两层：

1. **几何断言**（新增第 28 节）：把 iframe 临时调成 exe 的真实客户区尺寸
   （`1380×880`，取自 `launcher.cs` 的 `ClientSize`），然后量
   `#btn-start` 的 `bottom` 是否落在可视区内。
   判据刻意写成"**主按钮在可视区内**"，而不是"整页不许滚动" ——
   底部署名要滚一下才看全完全正常，重点是别让人找不到开始按钮。
2. **从结构上取消这一类问题**：
   - 结晶面板从标题页区块**改成弹窗**（和「玩法说明」同一套），
     标题页的职责收敛回"选职业 / 选难度 / 开始"三件事。
   - 操作区做成 `position: sticky; bottom: 0`，**永远贴在可视区底部**。
     为什么不是"算一个刚好装下的高度"：标题页的高度取决于窗口尺寸
     （卡片在窄窗口里会换行变高），算出来的值迟早会在某个尺寸上失守。
     sticky 之后这一整类问题都不存在了。

**事后复盘**：这个 bug 的形状是"**我加了一块内容，但从没量过它有多高**"。
以后往标题页加任何东西，先跑 `tools\probe_title.html`（本轮新建的取证工具），
它会直接告诉你内容高度、按钮位置、要不要滚动。

### 2. ESC 暂停菜单

顺手补上了玩家点名的 ESC 菜单。设计上有三处值得写下来：

**① Esc 的语义是"逐层往回退"，不是"一键回主菜单"。**
顺序写死在一个地方（`main.js` 的 keydown）：

```
背包 → 结晶面板 → 玩法说明 → 暂停菜单 → （都没开才）打开暂停菜单
```

为什么不让每个弹窗自己去抢 Esc：那样按键行为会**取决于谁的监听先挂上**，
改一处就可能把另一处弄坏。分层表写死，语义才稳定。

**② "暂停"在这个游戏里不是冻住模拟，而是拔掉输入。**
本作是回合制，本来就不会自己跑。所以菜单的真正职责是**挡住输入** ——
而门禁有**两处**（键盘事件 / 长按与鼠标共用的 `blocked` 变量），必须都堵上。
漏掉一处的症状就是"菜单开着，角色还在走"。

**③ `!ev.repeat` 是必须的。**
按住 Esc 时系统会持续发 keydown。少了这一条，就会出现
"关掉背包的那一次长按，紧接着把暂停菜单弹出来"。
这是写代码时才想到的，所以专门加了一条断言钉住它。

### 3. 两处旧测试被新语义"改坏"（这类失败要先分清责任）

改完 Esc 之后，冒烟里的旧键盘测试挂了 2 条：

```
FAIL 方向键没有让角色移动（尝试了 1826 个方向）
FAIL 空格没有消耗回合
```

原因不是产品坏了：那条测试中途按了一次 Esc（本意是"确保没有弹窗挡着"），
而**新语义下无弹窗时按 Esc 会打开暂停菜单** → 后面的按键全被菜单挡住。

> 教训：**改按键语义时，先搜一遍测试里所有按下这个键的地方。**
> 这类失败看起来像回归，其实是测试的预期跟不上新契约 ——
> 但直接"把测试改绿"是危险的，必须先确认产品行为是**想要的**，再改测试。

## v11.0 —— 区域化地图 · 无尽模式 · 本机排行榜 · 操作指南

四块新内容，以及**本轮真正踩到的坑**（最后一节比功能更值钱）。

### 1. 区域化：先问"玩家在这里要做什么决策"

原来的地图只有"怪多怪少"，走哪边都差不多 —— 那"往哪走"就不是决策。
v11 把每层切成 4~6 个区域（多源 BFS：种子点 + 最远点采样），
每个可走格恰好属于一个区域，每块地有一个类型（普通 / 精英 / 奖励 / 危险 / 守门）。

三个取舍：

- **不用"按房间划分"**。房间之间常只隔一条走廊，按房间分会切出一堆
  一两格的小区域 —— 既没玩法也没法标颜色。
- **第一层不设高难区**。它不是难度旋钮，而是教学层：玩家在头 20 步里
  要认识职业、试手感。开局撞进精英区，学到的不是"要不要绕开"，
  而是"这游戏只能硬碰硬"。
- **区域全部可见**。"看得见才谈得上规划"，没进去过的只用淡一档表示。

区域必须"真的有意义"，否则它只是一种颜色。所以：精英区里确实出现精英怪、
奖励区确实 ≤1 只怪 + 有宝箱 —— 这两条**扫 8 个种子**去验（见下面的坑②）。

### 2. 无尽模式：拿掉一条线，而不是加一个旋钮

它沿用这一局本来就选的 difficulty，只是把"到第 N 层结束"拿掉。
唯一的新东西是 `endlessBoost`：越过正篇层数之后每层再叠一档，**递减增量**。

> 线性增长到第 10 层就彻底打不动了，玩家会在一个固定层数上必死 ——
> "无尽"于是退化成"再看一遍第 9 层的死法"。

攻击力只吃 70% 的增幅（血厚是"打久一点"，攻高是"一下就死"）。
正篇之内倍率恒为 1，所以**不影响原有平衡** —— 这条有断言钉住。

### 3. 分数与排行榜：唯一执行点 + 反挂断言

分数公式只有一处（`data.js` 的 `scoreOf`），两个模式共用。
两处定价是有意的，而且都用断言钉住了：

- **难度乘系数，不加分**：加法会让"深渊 2 层"超过"标准 3 层"，
  最优解变成刷低难度。断言：休闲 5 层 < 标准 6 层 < 深渊 5 层。
- **通关奖励远高于多打一层**：否则最优解变成在门口反复刷怪。

写榜跑在和结晶结算**同一道幂等闸门**里 —— 结算是会被重绘的界面，
排在闸门外的写榜会把重复调用变成榜上好几条同样的记录，而榜删不掉。

### 4. 操作指南：抽成一份数据，然后真的按一遍

`data.js` 的 `KEYS` 是全项目唯一一份"按什么键做什么事"。指南按当前界面
过滤后渲染（局内 10 行 / 背包 2 行 / 选牌 2 行），冒烟测试**逐条按下去**验证。

> 比对两份文本只能证明"文档和代码写了同样的字"。
> 而且指南写着能按、实际按不动时，玩家会先怀疑自己按错了 —— 这类 bug
> 几乎不会被反馈回来。

### 5. 本轮踩到的坑（最贵的一节）

#### ① 补丁脚本不幂等 → 同一段代码被插进文件两遍

**同一个坑踩了两次。** 我的文本补丁是"锚点 → 替换"，而 `new` 里保留了 `old`
（为了让锚点仍然成立），于是**脚本一旦被执行两次，就会插入两份**。
后果不是"多一行注释"，而是 `const SCORE` 重复声明 —— **直接是语法错误**，
或者 C# 那边 `OnWebMessage` 重复定义、csc 报 CS0111。

> 对策（已落到本轮所有补丁脚本上）：**幂等守卫** ——
> 在替换前先检查 `new` 的唯一标记是否已存在于文件里；在就跳过。
> 再配合"改完立刻审计每个标记的出现次数"。

#### ② 「跳过 = 没测」：断言挂在随机条件上

第 35 节的"精英区真的有精英怪"原本写成 `if (eliteR) { ... }` ——
第一层恰好没有精英区时，整条断言**静默跳过**，看起来还是"全绿"。
（本轮加了"第一层不设高难区"之后，这个洞立刻暴露了：扫 8 个种子全空。）

> 对策：改成扫 8 个种子，并且**"一个都没扫到"本身就是失败**。
> 可变条件上的断言，要么保证跑得到，要么就是在装样子。

#### ③ 假通过：小地图像素采到了底色

"两个不同区域在小地图上颜色不同"这条断言，第一版采到的两个点**都是未探索格**，
读出来都是背景色 `rgb(6,9,17)` —— 而断言比的是"两点颜色不同"，
它比的是**另外两个点**，于是照样通过。看起来绿，其实什么都没验证。

> 对策：采样前把 `explored` 全打开；并额外断言"采到的不是底色"。

#### ④ 不要猜随机数给了什么

`_makeEnemy()` 的 `kind` 取决于敌人池，而池子里**本来就有 elite 原型**。
测试里"造一个普通怪然后断言精英计数不变"，于是假失败。

> 对策：显式 `fakeN.kind = 'normal'`。测试不能去猜随机数给了什么，要把它钉死。

#### ⑤ readFile 的行号与实际不符

`readFile` 报 smoke.html 1877 行，而 Python 按 `\n` 数是 2180 行 ——
两个数字都对不上时，**不要按行号定位**，一律用文本锚点或正则。
（同族教训：`Get-Content` 的行号也不可信。）

## 1. 为什么这一轮先做重构（a）

`_duel` 原来是一个 while 循环：一口气算完整场，再把 `res.log` 交给界面。
界面只能**回放**。玩家看得见谁先出手，但中间没有任何一个时刻能改变什么 ——
那不是"打仗"，是"看结算"。

拆成两件事之后：

```
newDuel(...)            建一场，返回一个可以逐轮推进的句柄
duel.step(玩家选的路)    推进**一轮**（双方各出手，含速度碾压 / 连击的追加击）
duel.runAuto(pick)      循环 step，直到分出胜负
```

于是 `fight()`（无头模拟、冒烟里的伤害数学、所有非交互路径）与战斗界面
走的是**同一个 step** —— 界面只是把 `pick` 换成了人在点按钮。
规则仍然只有一份。这条是硬要求：复刻一份核心逻辑已经踩过一次坑，
两份实现一旦漂移，平衡数据全是假的，而且过很久都不会有人发现。

**纯重构的验收标准是「逐位相同」，不是「看起来合理」**：
76.0 / 51.3 / 36.3，连 turns / kills / endDepth 分布都一模一样。

### 顺手抓到一个反直觉的性能坑

给 Game 实例新增字段 `this.liveFight` 会让它的隐藏类发生迁移，
`playHeadless` 里所有指向旧 map 的内联缓存随之全部重建。后果：

> 战斗本身只占整局的 1.5%，**整局却慢了 3 倍**（n=20：741ms → 2149ms）

定位过程比结论更值得记：

1. 先算「每局多出来的耗时 ÷ 新增的战斗调用次数」→ 单次 `newDuel` 要背 2.1ms，
   比微基准量到的 1µs 高三个数量级。这一步说明**假设错了**。
2. 于是转去量**整局**，把每个阶段都包上计时器 →
   `UNACCOUNTED (total - fight)` 从 715ms 涨到 2117ms，
   而战斗路径只从 26ms 变成 32ms。

**症状出现在离改动最远的地方。** 所以定位时不能只量改动的那一段，得量整局。

修法不是"删掉这个字段"，而是把它放到 `reset()` 里声明 ——
字段从出生就存在，没有迁移；无头路径则完全不碰它
（句柄由调用方持有，只有逐回合路径才显式存起来）。

## 2. 逐回合战斗（b）

### 2.1 先量清楚：战斗到底打几轮

这一步决定了整个提交该不该做。`tools/probe_fightlen.html`（n=60 标准）：

| 轮数 | 占比 | | 敌人类型 | 均轮数 | 一轮结束占比 |
|---|---|---|---|---|---|
| 1 轮 | **83%** | | 普通怪 | 1.09 | **92%** |
| 2 轮 | 13% | | 精英 | 1.49 | 66% |
| 3 轮 | 3% | | 首领 | 2.34 | 37% |
| 4~6 轮 | 1% | | | | |

而 `D.STANCE.every = 3`：姿态每 3 次行动翻一面。

**两个数字放在一起就把设计问题说清楚了**：83% 的仗在第 1 轮就结束，
所以对大多数战斗来说，"每轮选一次"只会弹一次 ——
那一轮的选择和"开战前选一次"是同一个决定，玩家并没有多做一个决定。

这正是这个计划自己写的否决条件：
*「只有手动选而无姿态轮换 = 玩家永远选最优 = 只是多一次点击、没有多一个决定。」*

所以 b 的正确形态不是"把菜单做漂亮"，而是**让姿态在战斗内轮换**：
一轮结束推进一次敌人的姿态时钟。只有在能打到第 4 轮以上的战斗里，
题目才会中途改变 —— 那恰好就是那些精英与首领。
菜单是为它们做的，同时也是 Phase 2 横板界面要用的容器。

### 2.2 一次被消融实验拦下的错误归因

第一版让 AI **每轮重掷**失误。跑出来 88.7 / 61.7 / 43.0，
比对照组高 10~12pp —— 看上去像"逐轮决策带来了巨大收益"。

那是模型错了。fumble 模拟的是"你有没有看准面板"；
面板一个字没变的时候重掷一次骰子，等于假设玩家每轮都会重新怀疑自己一次。

`tools/probe_stanceablation.html` 的四配置消融把它钉死：

| 配置 | standard | abyss |
|---|---|---|
| S0 姿态不轮换 / 开战选一次 | 51.3 | 36.3 |
| S1 姿态轮换 / 开战选一次 | **50.3** | **35.3** |
| S2 姿态轮换 / 每轮重掷 | 61.7 | 43.0 |

那 +11.4pp **全在 S1→S2 上**，和姿态轮换无关。
改成"只在题目变了的时候重新读"之后，机制的量级回到 ±1pp。

> 教训：当一次改动量出「远超预期」的收益时，先怀疑模型，再庆祝。

### 2.3 机制本身的量级：落在噪声带里

| 量法 | 休闲 | 标准 | 深渊 |
|---|---|---|---|
| f=0 隔离（两边随机流完全相同，只有机制在动） | — | +1.4 | +1.4 |
| S0 ↔ S1 消融（同随机流） | -1.0 | -1.0 | — |

而 n=300 自身对随机流的敏感性约 ±2pp。
结论：**这一批不动难度基线**，不需要补偿方案。
（原计划预期"通关率必然下移"，实测没有 —— 因为姿态对双方是对称的。）

### 2.4 边界：菜单里暂时没有魂技与撤离

- **魂技**：`useSkill()` 是在**地图层**结算的（读 `this.px/py`、写 `this.hp`）。
  对决进行中 `this.hp` 还没被 `_fightSettle` 写回，两套状态源会同时写同一个敌人。
  那正是这一路一直在踩的坑，所以先不接 —— 需要把 skill 结算搬进对决层。
- **撤离**：得先有"代价"，否则战斗全部可规避，掉落与击杀系统一起失去意义。
  代价的定价要单独一轮平衡测量，不该混在"让玩家自己选物法"这个提交里。

## 3. 高分辨率战斗立绘（c）

原来的做法是 `toCanvas(8)`：把 32×32 的小立绘拉大 8 倍。
**放大解决不了细节，只解决了"占多大地方"。**

改成三层，缺一层都不成立：

1. **几何层** `geo32(P, m)`：32 单位的坐标统一换算到原生像素。
   `heroGeo` / `monsterGeo` 里的坐标仍然写 32 单位 ——
   所以战斗立绘和地图小立绘**共用同一段形体代码**。
2. **细节层**：只在原生分辨率下画 —— 眼睛的三层结构、眉、发丝、布褶、
   金属高光，以及按 `body` 分派的皮肤纹理。
   这些东西在 32×32 上没有位置：那时候一只眼睛就是一格。
3. **明暗层** `bigShade`：逐像素的方向光梯度（方向和场景里那道 `.bs-shaft`
   一致，从左上打）+ 轮廓内暗边 + 在放大后的尺度上撒的细噪。
   只描一圈亮边是"贴纸感"的典型来源。

尺寸：英雄 96×96（3 倍），敌人 64×64（2 倍，它在画面里更远更小）。
两者都以**整数倍**放到屏幕上（288 / 192），配合 `image-rendering: pixelated`。

### 3.1 没有眼睛，怎么判断画得对不对

这是这一节真正的难点。所以退一步做两件**客观**的事
（`tools/probe_artview.html`）：

1. **把精灵按亮度梯度打成 ASCII 打出来** —— 判断不了"美不美"，
   但能判断"是不是一个完整的人 / 怪""脸有没有糊掉"。
2. **轮廓一致性断言** —— 大立绘按 mult 下采样后必须覆盖小立绘的轮廓
   （允许一格容差：`outline` 给小立绘加的是**一整格**，给大立绘加的是
   **一个原生像素**；同一个描边操作在不同分辨率下厚度本来就不一样）。
   它守的不是"好不好看"，而是**"还是不是同一个角色"** ——
   把"两套绘制器慢慢漂移"变成一个会红的测试。

### 3.2 它真的抓到了一个 bug

`geo32.ell` 原本把半径乘 m 之后交给 `PX.ell`，而 `PX.ell` 的扫描边界是
`floor/ceil(半径)` —— 乘 m 之后比"缩放后的边界"窄最多 `m-1` 个像素，
于是**椭圆最外一圈整圈丢掉**：每个怪少 10~15 格。

改成自己扫原生像素、边界向外多扫一格之后归零。
差异图（`#` 都有 / `S` 只有小 / `B` 只有大）让这件事一眼可见 ——
没有那张图，我只会在"缺 14 格"这个数字上原地打转。

## 5. 遗留

1. **战斗长度**是整个决策层的天花板。83% 的仗只有一轮，
   任何"每轮做一次决定"的机制都只能生效一次。
   要让菜单真正有价值，得先让战斗长到 2~3 轮 ——
   那是数值改动（双方 HP / 伤害曲线），会动全部三档基线，需要单独一轮。
2. 魂技进菜单、撤离、随从/站位（Phase 2 横板的前提）。
3. 战斗场景里 `runEvents` 不播战斗音效（`kind:'fight'` 在 `afterAction` 里
   被摘出来交给战斗场景，而战斗场景没有 `AU.play`）——
   这是 v11.2-h 就存在的缺口，本轮没动。
