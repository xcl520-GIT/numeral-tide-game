# v11.11 · E：地图内容量 —— 新的区域类型「柱厅」

> 「目前玩下来是有点类 rogue 的感觉，但是**每层的变化感觉不大**……

路宽（P2）与区域标签矛盾（v11 早期）都已解决；**剩下的是"地图本身长得不一样"**。

## 一、为什么单开一个"地形型"的轴

已有的四种区域其实只分两类：

| 轴 | 谁 | 改的是什么 |
| :--- | :--- | :--- |
| 难度型 | `elite` / `hazard` | **敌人强度** —— 这一区有多难 |
| 休整型 | `reward` | **敌人数量** —— 这一区安不安全 |
| **地形型（新）** | **`pillar` 柱厅** | **地形的形状** —— 这一区**长什么样** |

"每层的变化感觉不大"这句话，前两类一条都解决不了：怪强一点、怪少一点，
地图**长得还是同一个样子**。柱厅改的是形状，于是它同时给三样东西：

1. **一眼**：进区就看得出这一区不一样（石柱 + 小地图配色 + 区域横幅）；
2. **掩体**：埋下去的石柱**同时挡视线**（WALL 在 `OPAQUE` 里）——
   而 v11.11 刚做的远程怪第一次让"视线"变成一条真的战术资源（看不见就不许开火），
   于是"石柱"和"箭"这两件事在同一版里接上了；
3. **卡位**：窄口变多，"被围住"与"甩开它"的代价同时上升。

`danger` 给 **1**、`enemMul` 给 **1.00**：它是地形型，不是难度型。
把它标成高危险会让 HUD 那排星开始撒谎，而"标签撒谎比没有标签更糟"这条规矩
在敌人标签那边已经写过一次。

**池子里放两份**：实测放一份时 24 层只出现 5 个柱厅（约 21% 的层），
而这一项要解决的正是"变化感觉不到"—— 三层才撞见一次，等于没改。
放两份后实测 10/24（约 42% 的层），代价是其余三种特色区各从 1/7 降到 1/8。

## 二、落地：四条边界 + 一条**精确**复验

实现只有一个方法 `_carvePillars(reg)`（`core.js`），跑在 `_buildRegions` 的末尾
—— **必须在 `_spawnEnemies()` 之前**（否则会把怪埋进柱子里，见第三节）。

**为什么按时装撒、不随机撒**（`data.js` 的 `MAP.pillarStep: 2`）：
随机撒只能靠连通性兜底收拾残局，而兜底一旦被触发，地图上就多一条笔直的应急走廊
（`_ensureConnectivity` 凿的）—— 那是"修好了"，但玩家看到的是一条不该出现的路。
按时装（只埋横纵坐标都是 `step` 的倍数的那种格）有一条现成的性质：
**石柱之间天生留着网格状的空档**，任何一格都能绕开柱子走。兜底仍然留着，但正常不响。

四条不许碰的边界，每一条砸掉都会直接弄坏别的机制：

| | 边界 | 砸掉的后果 |
| :- | :--- | :--- |
| ① | 邻接**别的区域**的格绝不埋 | 那是"门位"，堵掉它 = 切断两个区域之间唯一的通道（`_regionDoors` 排队、区域门禁放行都靠它） |
| ② | 只动普通地面（FLOOR / MOSS） | 水要留给潮汐按水位重算；宝箱 / 泉水 / 商栈 / 门都有主 |
| ③ | 玩家脚下、出口格、**有怪站着的格** | 不用解释 |
| ④ | `tiles` 与 `base` 必须同步 | 不同步 = 退潮时石柱被冲掉（"逻辑上有柱子、画面上没有"） |

**复验是精确的**，不是"看起来没事"：

```js
const before = this._reachCount();
...埋下去...
if (this._reachCount() !== before - cand.length) { 整块还原; reg.type = 'normal'; return -1; }
```

埋掉的每一格都该是"多余的路"，所以可达格数应当**精确地**减少 `cand.length` 个。
差一个就说明有地方被隔断了 —— 整块还原，并把这一区退回普通区。
（宁可没有柱厅，也不要一个把敌人关在外面的柱厅：那只会表现为"这一层莫名少了一只怪"，
是最难归因的一种。这是本项目"地图生错了不能靠调数值掩盖、必须有确定性兜底"的同一条纪律。）

## 三、过程中被新断言抓出来的两个缺陷

第 58 节是拿**一只已经建好的关卡**去试这个函数的 —— 它当场抓出两件事，
两件都不是柱厅本身的逻辑错，而是"边界没想到"：

### ① 柱子会把**已经存在的怪**埋进去（已修）

第一版只跳过了玩家脚下与出口格，**没跳过敌人**。于是埋完就有怪站在石柱里，
它随即变成"走不到的敌人"，而 `_ensureConnectivity()` 会把它**静默删掉** ——
表现出来只是"这一层莫名少了两只怪"。

修法：加一句 `if (this.enemyAt(x, y)) continue;`。
它的意义不是"当前调用路径需要它"（当前路径在布点之前，这一条恒不成立），
而是 **"这个函数在任何时机被调用都安全"** —— 而冒烟正是拿"任何时机"在试它。

### ② **孤岛口袋里的怪从来没被清理过**（已修，且是一条更早的遗留缺陷）

修完 ①，扫描仍然报 `seed58408:敌人不可达`。取证（`probe_pillar_unreach.html`）：

```
depth=4  exit=9,27  connectedFix=0  enemies=14
regions: 0:gate/73格  1:pillar(柱13)/85格  2:normal/36格  3:normal/353格  4:normal/96格
孤岛口袋（可走但走不到）= 36 格   例如 4,4 5,4 6,4 7,4 8,4 …
!! 不可达的敌人: titan/elite @7,5 tile=1(FLOOR) walkable=true region=2(normal)
!! 不可达的敌人: archer/normal @6,4 tile=4(MOSS) walkable=true region=2(normal)
（共 4 只，全在区域 2 = 那 36 格的孤岛口袋里）
```

三点证据说明**与柱厅无关**：怪站在**可走的**地面上（不是被柱子埋的）、
它们所在的是 `normal` 区（不是柱厅区）、而且`connectedFix=0`
（真把一整块隔断的话，那条"精确减少"的复验会当场拦下并还原）。

根因在别处：`_ensureConnectivity()` 只在分区**之前**被调用过一次
（那是刻意的 —— 它凿墙、增加可走格，分区必须在它之后），
**而那一刻还没有敌人** ⇒ 它里面那段"走不到的敌人留在场上只有坏处"
**从来没有执行过，是死代码**。map 生成可以留下一整块走不到的口袋
（这里 36 格，正好是一个区的面积），怪住进去就永远杀不到、AI 会一直往上撞。

修法：在 `_applyRegionFlavor()` 之后**再调一次** `_ensureConnectivity()`
（函数是幂等的：出口已经可达时它一次墙都不会凿）。它同时服务两个目的：
补上那段死代码，以及给柱厅这条复验配一道**结构性的**后手。

- 方向是**略变容易**（+0.9 ~ +2.4pp），两条解释都成立且都无害：
  ①孤岛口袋的敌人不再出现在场上（受影响的那几层少了几只打不到的怪）；
  ②柱厅给掩体（远程怪的出手机会变少）。
- 第 1 层死亡 休闲 +11.9%（42 → 47）**必须照实记**：
  第 1 层按设计不设柱厅，所以这个数不是因为柱子 —— 它是"加条目会重排随机流"
  那条读数纪律的又一次体现（D 那一项里已经写清：**n=900 才算尺子，单层死亡数
  在 n=900 下摆动 ±10% 属于正常**。绝对值只有 5 局。）

> **回退**：把 `'pillar'` 从 `pool` 里删掉即可（`_carvePillars` 与复验都不影响别的区域）。

## 六、没有做的那一半：地图**更大**

反馈第 1 条与第 2 条都提到"地图可以再大一点"。**这一轮不做**，理由写在下面，
免得下次又被当成"漏了"：

- 地图更大 ≠ 变化更多。这张图本来就约 **40% 是空的**（空房间是刻意的节奏呼吸点，
  见 `_spawnEnemies` 的注释）；单纯把 45×35 放大，只会把空区占比推得更高、
  把"走过去"的时间拉长，而**内容密度不变**。
- "绕开的自由度"这件事，v11.5 P2 已经用**路宽 2** 从另一个角度解决过
  （反馈原文是同一句里的"适当增大路的宽度"）。
- 真要变大，正确的顺序是**先有更多种区域与布局**（这一轮做的），再按内容量扩图；
  反过来做会得到一个"更大更空"的地图，那正是玩家在抱怨的东西。

⇒ 这条列进"下一步"，与 E 的其余部分（更多区域类型 / 布局模板）放在一起。
